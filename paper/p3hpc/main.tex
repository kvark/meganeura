\begin{abstract}
Can graphics APIs carry machine-learning training and inference across
consumer and server GPUs? \system{} lowers tensor graphs and their gradients
to Vulkan and Metal, selecting graph forms and kernel schedules by measurement.
We evaluate five workloads under strict-f32 and accelerated contracts on eleven
GPUs from five vendors. All 330 core native qualification cells pass; seven
GPUs supply replicated performance measurements. Including larger language
models, 246 native performance cells qualify and 226 admit a paired comparison
with compiled PyTorch~2.13. On the core matrix, median native/PyTorch time
ratios are 1.35 for inference and 1.61 for forward--loss--backward under strict
f32, and 2.06 and 2.21 accelerated. These aggregates are conditional on both
engines passing the declared numerical gates; loosening the gates could change
both eligibility and the kernels selected by search. Experimental Mesa and
AMDGPU patches enable MI300X Vulkan execution up to 1.7B parameters. Three
integrated GPUs and a Quest~3S supply correctness-only evidence, while a
separate XR deployment shares its Vulkan queue with rendering. Coverage is
broad, but matrix features alone do not close the performance gap; arithmetic
policy, driver support, preparation cost, and timing variability remain limits.

\end{abstract}

\section{Introduction}

High-performance computing (HPC) uses portability layers such as Kokkos,
RAJA, and SYCL to write one program for heterogeneous hardware
\cite{edwards2014kokkos,beckingsale2019raja,khronos2020sycl}. Graphics APIs
offer another route for machine learning (ML). Vulkan runs on NVIDIA, AMD,
Intel, Qualcomm, and Arm GPUs, and Metal on Apple devices
\cite{khronos2026vulkan,apple2026metal}. An application that already renders
through these APIs can give its device, memory, and queue to a tensor runtime.
Games, simulators, and XR applications could then run ML without shipping a
second GPU stack. This paper measures what that choice gains in hardware
coverage and what it costs in speed.

\system{} is our test of the idea. It is a native compiler and runtime,
implemented in Rust with WGSL shaders. It lowers a typed
tensor graph, and the training graph that automatic differentiation derives
from it, to generated compute kernels. It runs them through Blade, a thin
Vulkan and Metal layer \cite{malyshau2026barriers}. Training and inference
share the compiler, checkpoint format, and runtime on every device.
Compilation can also time alternative graphs and kernels on the target GPU
before committing to a plan. That search is optional; the main measurements
enable it with a soft 30-second budget per session.

We compare \system{} with PyTorch~2.13 \cite{paszke2019pytorch}, compiled
with \code{torch.compile} and replayed as whole-phase CUDA, HIP, or XPU graphs
where the backend allows it. The baseline therefore avoids per-operator Python
overhead, and vendor libraries do much of its work. The main comparison
covers seven GPUs from NVIDIA, AMD, Intel, and Apple, on Linux, Windows, and
macOS, with five workloads under two arithmetic contracts. Every timed result
must first pass numerical checks. Three additional integrated GPUs use CPU
f32 references, and an Android Quest~3S uses a full-tensor CPU f64 oracle.
These four platforms contribute correctness evidence, not performance ratios.

The final collection, completed in October 2026, uses one frozen compiler
and harness revision. MI300X runs the same native engine as the consumer
GPUs, through experimental Mesa and AMDGPU patches. This establishes a
working Vulkan compute path on the tested accelerator, not Vulkan conformance
or stock-driver support. The core matrix covers eleven GPUs from five
vendors; the timed comparison covers seven GPUs from four vendors.

PyTorch remains faster in most paired comparisons. \system{} performs well
on the RX~7900~XT and loses every paired core phase on the Arc~B570.
Rectangular tiles, BF16 matrix candidates, and NVIDIA workgroup-scope
cooperative matrices are enabled in this revision. Their availability does
not imply that search selects them, nor that a selected kernel matches a
vendor library. We report missing references and timing ranges alongside
speed, and distinguish numerical-policy failures from execution failures.

Our contributions are:
\begin{itemize}
  \item A numerically checked comparison of a compact graphics-API ML stack
        with compiled PyTorch on seven GPUs from four vendors, including the
        points where each stack fails (Sections~\ref{sec:method}
        and~\ref{sec:results}).
  \item A qualified Vulkan compute path on MI300X, with recorded driver
        patches, arithmetic capabilities, and reference workarounds
        (Section~\ref{sec:availability}).
  \item Measurements of compile-time graph and kernel search: the alternatives
        it selects, numerical rejections, and preparation costs
        (Section~\ref{sec:search}).

  \item Deployment evidence beyond the main matrix: Vulkan qualification on
        three integrated GPUs and a Quest~3S, models up to 1.7 billion parameters, and an
        Android XR application sharing its Vulkan queue with rendering
        (Sections~\ref{sec:results} and~\ref{sec:edge}).
\end{itemize}
We do not measure production-scale language-model training, optimizer
updates in the timed step, distributed execution, or scientific simulation.

\system{} executes a typed, static tensor graph (Fig.~\ref{fig:pipeline}).
Graphs come from native builders or from Open Neural Network Exchange (ONNX)
and Neural Network Exchange Format (NNEF) importers. A GGUF file stores
weights and an architecture description but no graph, so an optional loader
builds the graph that the architecture implies and fills it from the file. Rewrites run in egglog,
which keeps equivalent forms of an expression in an e-graph rather than
committing to the first profitable rewrite \cite{zhang2023egglog}. For
example, the query, key, and value projections of an attention block can
stay three matrix products or become one packed product, and the e-graph
holds both. Saturation is bounded: small graphs are explored whole, larger
ones through one repeated region, such as a transformer block, that is
verified to recur. Precision changes and in-place updates end a region.
Reverse-mode differentiation builds the training graph, and an application
can add a stochastic gradient descent (SGD) or Adam update; the benchmark
leaves the update out.

Matrix schedules live in the same e-graph. Tile sizes, K staging, counted or
unrolled loops, and split-K reductions are equalities, as are transposed and
packed products. Without search, the compiler extracts one graph by estimated
tensor traffic and leaves kernel parameters to heuristics. That estimate
counts logical bytes; it has no model of caches, arithmetic, occupancy, or
launch cost. A gradient product inherits its forward schedule where that is
legal. After differentiation, search also explores independent attention
gradient layouts for queries and for keys/values. Forward graph and backward
layout choices are interleaved within the same candidate limit. Native f32
matrix and attention implementations use the cooperative tile sizes the
device exposes. Some choices, such as direct versus Winograd convolution,
still follow shape rules.

Code generation uses a few kernel families: pointwise expressions,
reductions, general matrix multiplication (GEMM), convolutions and their
derivatives, and tiled attention. Shape, device capabilities, and the
arithmetic contract decide which implementations are legal and how
workgroups are shaped. Kernels are emitted as WebGPU Shading Language (WGSL)
\cite{w3c2026wgsl}, validated by Naga, and translated by Blade into native
Vulkan or Metal pipelines. Naga is shared with wgpu; the wgpu runtime is not
used. The compiler fixes a dispatch sequence and a memory plan that reuses
buffers by lifetime. Each step records and submits that plan without
rediscovering the graph or allocating tensors, although command recording
and synchronization still happen every step. The PyTorch baseline gets the
equivalent through graph replay.

When search is enabled, every candidate is built in a private session with
representative weights and inputs. The search checks it against the untuned
ordinary build, tunes its kernels, and then races complete programs with fresh
command recording and submission. A challenger replaces the incumbent only
if it passes the numerical checks and beats it by more than the measured
noise, so graph forms compete after tuning instead of being discarded by the
cost estimate. Dispatch fusion and attention and convolution splits vary as
well, including up to 64 submission chunks per step. The policy measured here allows at
most 16 graph and schedule forms and 64 candidate programs in total per
session, within a soft 30-second deadline and 1\,GiB of scratch memory for
kernel probes.

Kernel alternatives are raced together, with a 5\% kernel improvement
threshold; a whole-program challenger must improve by at least 1\% and
clear the timing-noise margin. Candidate qualification is followed by two
final executions of the selected program. Persisted kernel-class decisions
are shared within each campaign/model/profile, while whole-program search
runs afresh. Thus later processes can reuse kernel decisions without hiding
that state in an ostensibly cold preparation measurement.

\section{Checking the Compiler and Its Kernels}
\label{sec:validation}

Comparing two frameworks is useful, but when they disagree it does not say
which one is wrong, and a deterministic indexing bug repeats perfectly. \system{}'s test suite therefore checks the compiler
against an independent reference in three
ways.\footnote{\href{https://github.com/kvark/meganeura/tree/c19cb1caedd90be7abc61de61f6197018711398e/src/reference}{Reference interpreter and checks at the measured revision}.}

First, a small CPU interpreter evaluates every graph operator in 64-bit
floating point and shares no lowering or shader code with the GPU path.
Inputs are rounded to their storage precision first. Symbolic derivatives
evaluated by the interpreter are compared with central finite differences.
Nonuniform weighted losses and directional probes ensure that gradients are
tested beyond an all-ones upstream derivative.

Second, operator sweeps compare every GPU output and gradient element with the
interpreter, on shapes chosen to hit tile edges, reduction splits, and
alternative lowerings. The tolerance scales per element and uses sums of
absolute products for reductions prone to cancellation. It is a practical
error model rather than a proof. Third, composed blocks and seeded random
graphs pass through differentiation, e-graph optimization, dispatch fusion,
and memory planning. Their outputs and gradients, including gradients that
the optimizer packed, are compared with the unoptimized reference. Storage
starts filled with NaNs, so a missing write or an invalid buffer reuse shows
up.

These checks found real bugs: parameter gradients dropped during fusion, loss
reductions that were not scalar, cancellation in normalization, and vanishing
GELU tails. In the DinoVision application (Section~\ref{sec:edge}), a
LayerScale layout error updated only the first token while the output images
still looked plausible, and only an independent reference caught it. Adding
an operator to the IR requires either a reference implementation or an
explicit unsupported result; packed quantized formats are unsupported. None
of this covers every shape, schedule, driver, or device, so the benchmark
adds its own gates (Section~\ref{sec:gates}).

\section{Methodology}
\label{sec:method}

\inferena{}, our open-source cross-framework harness, builds matched
workloads, alternates engine order, synchronizes timing boundaries, and
records raw samples, outputs, gradient norms, revisions, and environment
metadata.\footnote{\href{https://github.com/kvark/inferena/tree/add19182e5479e3f7549894c524ac6691d3dc363}{Inferena source, revision \code{add19182}}.}
It supplies kernels to neither engine.

\subsection{Revisions and reference policy}
\label{sec:reference-policy}

All runs use \inferena{} \code{add19182}, \system{} \code{c19cb1c}, and
Blade \code{4845d65}. Every PyTorch wheel reports version 2.13.0 at source
commit \code{cf30153}, with Python 3.13.13: \code{+cu130} for NVIDIA,
\code{+rocm7.2} for AMD, \code{+xpu} for Arc, and the macOS wheel with MPS
for Apple. Drivers, host CPUs, and vendor libraries still differ between
platforms, so a common PyTorch revision does not make the backends identical.

PyTorch uses \code{torch.compile} with default settings. Max-autotune,
GEMM and pointwise autotuning, and coordinate-descent tuning are off. The
compiler's and vendor libraries' own heuristics still apply
\cite{pytorch2026compile}. We did not use max-autotune because it was costly
and unreliable during bring-up. It compiled for a long time on H100, its
convolution searches failed on both Radeons, and it did not finish its first
ResNet check on Arc within an hour.\footnote{\href{https://github.com/kvark/inferena/blob/add19182e5479e3f7549894c524ac6691d3dc363/EXPERIMENT.md}{Inferena protocol and bring-up notes, revision \code{add19182}}.}
A supervisor gives compilation 120 seconds for the first forward, backward,
and minimal-shape calls, and terminates the compiler on timeout. The engines
therefore prepare under different budgets. This is neither an equal-budget
contest nor a comparison with the best PyTorch result after hours of search.

CUDA and ROCm replay each phase through \path{torch.cuda.CUDAGraph}, which
ROCm maps to HIP graphs, and Intel through \path{torch.xpu.XPUGraph}
\cite{pytorch2026hip,pytorch2026xpugraph}. Inductor's own CUDA-graph
mechanism is disabled, so the explicit capture is the only replay. XPU
capture needs two recorded accommodations: the math scaled-dot-product
attention (SDPA) backend and an equivalent formulation of embedding backward
(Section~\ref{sec:availability}). MPS compiles every phase but has no public
whole-phase replay \cite{pytorch2026mpssource}. No failed compiled or
captured phase falls back to eager or CPU execution.

Each process times three phases: a forward pass without gradients at the
full shape, a forward pass at a minimal shape, and forward--loss--backward
(F+L+B) without an optimizer update. For SmolLM2, the full forward is a
128-token prefill, and the minimal one is a single token without a key/value
cache, so it is not decode latency. The diffusion U-Net and Whisper already
run at batch one, so their minimal and full shapes coincide. Each phase warms
up for at least five calls and ten seconds, then records 20 synchronized
host-wall samples. Input upload and output readback happen outside the timed
interval.

Each condition runs in three fresh process pairs, with alternating engine
order and rotating condition order. We report the median of the three
per-process medians and keep every sample and the range. A phase enters an
aggregate only with three qualified pairs, where \emph{qualified} means it
passed the gates of Section~\ref{sec:gates}. A failed backward pass does not
discard a qualified forward pass, and no eager run or older result fills a
missing one.

\subsection{Arithmetic contracts}
\label{sec:contracts}

There are two profiles, not separate benchmark columns for each dtype.
Strict f32 disables TF32 and reduced-input-precision matrix operations.
Native f32 cooperative tiles remain legal: M3 exposes $8\times8\times8$
and MI300X $16\times16\times16$ tiles. Strict fixes arithmetic width,
not reduction order.

Accelerated permits reduced precision subject to qualification. PyTorch's
\code{auto} policy chooses BF16 on CUDA/HIP/XPU when the backend reports
hardware support, otherwise FP16; MPS uses FP16. This choice precedes
compilation and qualification, with no numerical-failure or timing-based
dtype retry. A declared exception keeps SmolLM2-135M's one-token phase in
f32; the larger models retain autocast there. Parameters remain f32, while
autocast chooses activation and operator types. FP16 training includes
GradScaler's scaling, unscaling, finite checks, and scale update inside the
timed step, but no parameter update. Remaining f32 operations have TF32
disabled in these runs.

\system{} retains f32 tensors and accumulation, with conversions inside
each timed step. Search may use f16 cooperative forward kernels or explicit
BF16 matrix-input candidates, as well as retain the f32 baseline. Derivative
regions remain f32. This is not the same computation as PyTorch's autocast
forward and backward. Rectangular subgroup shapes and NVIDIA workgroup-scope
tiles are legal where the recorded device capabilities permit them.

\subsection{Numerical gates}
\label{sec:gates}

The gates define the eligible implementations. Relaxing them could admit
faster kernels, tile shapes, reduction orders, or lower precision in either
engine, including programs rejected during \system{} search. These are
performance results under a frozen policy, not a tolerance-independent
ranking or an accuracy--performance frontier. We did not measure sensitivity
to wider gates. A common profile does not make the qualification procedures
identical.

\emph{Native fidelity.} Before precision conversion or search, an untuned
build of the original graph supplies a strict-f32 full-tensor oracle.
Strict candidates must satisfy maximum- and RMS-error bounds
$10^{-6}+10^{-4}r$, where $r$ is the corresponding reference scale.
Accelerated non-language-model outputs use coefficient 0.02, and the full
training-gradient vector uses 0.01. Accelerated language-model inference
instead gates the output distribution: mean token KL divergence at most
$\log(1.01)$, worst-token KL at most $\log(1.10)$, and mean loss deviation
at most $10^{-6}+0.02|L_{\rm ref}|$. Final selected-program executions must
also repeat within the declared bounds. Search cannot replace a qualified
incumbent with a rejected candidate.

\emph{PyTorch fidelity and training.} Accelerated forward uses an eager
strict-f32 oracle with the same non-LM output or LM distribution bounds.
Training additionally uses matched SGD trajectories: 256 updates on frozen,
varying real-text batches for every SmolLM2 size, with probe and held-out
checkpoints, or 32 repeated-input updates for the other models. The loss
bounds are 2\% plus $10^{-6}$; all requested updates must complete with
finite values. All trainable parameters update; a named parameter is also
checked as a sentinel. These untimed checks restore state before timing.
\system{}'s cohort gate checks full single-step gradients, not the same
256-step trajectory for every selected program. Neither procedure establishes
equal learning quality or substitutes for the other.

\emph{Repeatability.} PyTorch compares all output and gradient elements
across two uncaptured calls (eight for accelerated training), and two graph
replays when capture is used. Output and strict-gradient bounds use
$10^{-6}+10^{-4}r$; accelerated gradients use a whole-vector coefficient of
0.01. Repeating a value does not independently establish its correctness.

\emph{Cross-engine comparison.} Sampled outputs (256 positions) and loss
must agree within 1\%, and total gradient norm and the vector of parameter
norms within 5\% for strict. Accelerated allows 10\% per process but requires
the three-process median below 5\%. Packed gradients are restored to
checkpoint coordinates. Accelerated comparisons use preserved original
strict-f32 snapshots from both engines, not rejected AMP outputs as ground
truth; each measured candidate separately passes its fidelity gate. Samples
and norms can miss local or sign errors, motivating the full native checks.

A failed compiled reference supplies no timing ratio. Preserved f32
snapshots or checked eager diagnostics can independently qualify native
results, without replacing compiled timing. Numerical rejection means
failure of the declared contract, not a vendor defect or unusable application
accuracy. \system{} searches qualified alternatives; PyTorch uses a fixed
model/backend dtype policy. Coverage therefore also reflects different
preparation policies, not the best qualified implementation each stack could
possibly supply.

\subsection{Performance}
\label{sec:performance}

Table~\ref{tab:performance} gives every core ratio. Across seven platforms,
strict median ratios are 1.35 for inference (35 pairs), 1.03 for minimal shape
(33), and 1.61 for training (33). Nominal native wins are 10, 15, and 4,
respectively. Accelerated medians are 2.06, 1.49, and 2.21, each over 32
qualified pairs, with 4, 13, and 4 nominal wins. The sets differ: these
aggregates do not by themselves measure the effect of changing precision.
Wins describe median ordering, not statistical significance.

RX~7900~XT remains strong under strict f32: SmolLM2 prefill, one-token
forward, and training ratios are 0.61, 0.19, and 0.67. B570 loses every core
paired phase under both profiles; its SmolLM2 training takes 50.83\,ms
against PyTorch's 17.40\,ms strict and 12.59\,ms accelerated. On RTX~5070,
SmolLM2 prefill takes 6.28 versus 6.07\,ms strict, and 5.55 versus 2.96\,ms
accelerated. Native improvements therefore coexist with a larger gap to AMP.

MI300X's strict 135M prefill and training ratios are 1.90 and 2.29. Its
native-f32 matrix support enables a different kernel path without changing
the strict contract; it does not establish whole-program parity with ROCm.
On H100, accelerated 135M training is 17.49 versus 4.77\,ms. The remaining
gap is real even where other PyTorch conditions fail qualification.

We retain every process and sample. Define process spread as
$(\max t-\min t)/\operatorname{median}(t)$ over process medians. M3's median
spread across the two engines is 33.84\%, with 59 of 60 phase groups above
10\%, despite sleep prevention. No clock/power trace establishes the cause;
small M3 wins are not robust conclusions. Seven of 60 B570 groups exceed
10\%. H100 has one isolated native accelerated diffusion minimal-shape
outlier: 1.773, 5.310, and 1.772\,ms, with the same selected graph and chunk
count. Its PyTorch comparison is already unavailable. The accompanying CSV
preserves all process medians and paired-ratio ranges; none is discarded.

\subsection{Where the time goes}
\label{sec:gaps}

Host-wall time includes command recording, submission, waiting, and GPU
execution. Neither a near-parity minimal-shape ratio nor a larger-model
speedup gives an upper bound on barrier or submission overhead. Separating
those costs requires a controlled execution experiment or a device timeline.

The measured stack supports \code{VK\_NV\_cooperative\_matrix2}
\cite{khronos2024cooperative2}. Selected accelerated SmolLM2 programs on
both RTX~5070 and H100 reuse f16 workgroup-cooperative kernel choices, so
the H100 gap cannot simply be attributed to a missing extension. Yet the
native program keeps tensors and backward regions in f32, whereas PyTorch
uses AMP. Equal hardware support does not imply equal instructions,
conversion traffic, occupancy, fusion, or matrix coverage. The collection
contains no matched-kernel disassembly or feature-off ablation that isolates
these factors.

B570 advertises rectangular $8\times16\times16$ f16/f32 and BF16/f32
shapes, and the measured compiler accepts them. Nevertheless, its 42
accelerated core sessions select no cooperative dispatches. RTX~5070 selects
BF16 matrix dispatches in three of 42 accelerated sessions; H100 selects
none. MI300X's Vulkan driver advertises no BF16 capability, although ROCm
PyTorch uses BF16. Thus BF16 permission, device exposure, candidate
qualification, and final selection are distinct. These records demonstrate
limited use of the new paths, not a general performance benefit from enabling
them. A tolerance sweep would require rerunning search for both engines;
reclassifying stored rejections cannot supply that experiment.

The missing performance references have distinct causes. RX~7900~XT
strict Whisper fails training-output repeatability in all three processes;
MI300X strict ResNet fails gradient repeatability. Their later minimal-shape
phases are not attempted. MI300X accelerated diffusion and Whisper fail

B570 360M is different: the first strict PyTorch process throws
``wait method cannot be used for an event associated with a command graph''
during compiled backward capture. The stack places the wait below an
Inductor-generated operator in the XPU/SYCL path. This supports a captured
execution compatibility failure, not a diagnosis of a specific driver bug.
The harness also fails to classify it as recoverable and stops the campaign.
Native execution completes its internal checks, but has no independent
reference, no accelerated process, and no three-process replication. All
six requested cells are excluded from qualified results. Earlier uncaptured
diagnostics are not substituted. The small-model XPU path retains its
recorded math-SDPA and equivalent embedding-backward accommodations.

MI300X supplies a qualified accelerator path. Its
Vulkan path now passes every main and larger-model condition, using the
same unmodified \system{} and \inferena{} revisions as the other platforms.
The recorded device is \emph{AMD Instinct MI300X VF (RADV GFX940)}, with
304 compute units and about 192\,GiB of device memory. Mesa's experimental
CDNA path and our driver changes provide buffer-based compute and cooperative
matrices \cite{mesa2025cdna,malyshau2026mi300}; general image support and
Vulkan conformance are outside this result.

The setup requires both user-space and kernel changes. The measured Mesa
source and build string identify \code{8c7f5fdd}. The AMDGPU patch targets vendor source
\code{amdgpu-6.19.14-2364437.24.04}, built for Linux
\code{6.8.0-146-generic}. A native interface coordinates work across the
eight XCC compute dies; \code{mi300\_xcc\_gang=1} enables it.
The archives retain the patch series, build and module identity, launcher,
and a finite 60-second compute watchdog setting. These are experimental
driver requirements, not features of an unmodified distribution.

The reference also needs a recorded accommodation:
\path{MIOPEN_DEBUG_CONV_IMPLICIT_GEMM_ASM_FWD_GTC_XDLOPS_NHWC=0}
excludes a previously problematic convolution solver. This override is in
the MI300 provenance files, although the collector's generic
\code{runtime\_overrides} field is empty. The official collector, numerical
thresholds, compilation policy, and timing samples are unchanged. The passing
comparisons establish a working pair of explicitly configured stacks; they do not show that either stock installation works
without intervention.

\subsection{What it explores}

The 588 core sessions record 23,669 whole-program trials, 13 numerical
rejections, and 34 scratch-limit outcomes (Table~\ref{tab:search}). Resource
limits are not numerical failures; these are neither counts of independent
algorithms nor kernel-probe rejection counts. Whole-program timing remains the final
selection gate after kernel tuning. The search includes graph layouts,
fusion, attention splits, matrix inputs, and submission chunking. Device
features only supply candidates: the B570 and BF16 selection results in
Section~\ref{sec:gaps} show why capability exposure alone is insufficient.

The 30-second budget is per session, with at most 16 graph forms and 64
programs, and a 1\,GiB kernel-probe scratch limit. A workload builds three
sessions, or two for Whisper. The deadline is soft; original-f32 oracle
preparation lies outside it but inside native preparation time. The main
cohort has no feature-off, search-off, or alternate-budget arm. Historical
search studies use different revisions and policies and do not establish
the gain of this final configuration.

Native preparation includes graph construction, differentiation, pipeline

\section{Deployment Beyond the Matrix}
\label{sec:edge}

\begin{figure}[t]
  \centering
  \includegraphics[width=0.5\columnwidth]{../figures/dinovision-quest3s.jpg}
  \caption{DinoVision's live RGB reconstruction on a Quest~3S, captured
  from the headset's cast.}
  \label{fig:dinovision}
\end{figure}

The separately versioned application study below predates the final cohort;
its samples do not enter framework ratios. The case that motivates a graphics-API ML stack is an application that
already renders. DinoVision is one such application. It runs on the
Qualcomm Adreno GPU of a Meta Quest~3S under Android and reconstructs the
headset cameras' images from features of a DINOv3 vision encoder
\cite{simeoni2025dinov3} (Fig.~\ref{fig:dinovision}). \system{} trains the
2.01-million-parameter decoder on a desktop GPU with Adam and saves the
checkpoint. The headset loads it into a joined batch-one encoder/decoder
graph. The deployed graph performs 2.359 billion multiply--accumulates and
uses the same graph representation, compiler, memory planner, checkpoint
format, and Blade runtime as the benchmark. Two asynchronous eye sessions
share Blade's Vulkan context and queue with the OpenXR renderer.

We checked two things. First, for one fixed public RGB frame and identical
weights, the preprocessed patches are bit-exact between desktop and headset.
The encoder output agrees to a relative L2 error of 0.001059, and the final
reconstruction to 0.000457. Second, sharing the queue changes what the right
schedule is. In isolation, the graph runs in 96.78\,ms as one submission, and
splitting it into two chunks costs 4.1\%. During a 90-second live stereo
session, the two-chunk plan instead raises the application's render
submissions by 18.8\% and the slower eye's update rate by 8.7\%, and cuts
median worker latency by 20.2\%. Larger chunk counts help less, and
unevenly. The best plan for the renderer is not the best in isolation, and
one shared graphics stack lets the application choose it. This is a
deployment check, not an on-device training or PyTorch-on-Android
comparison. The weights, raw samples, manifests, and full-resolution media
are in the public
\href{https://huggingface.co/mad-bot/dinovision/tree/2c3f9017fe74c41482b165890c14737a2ccd4b6a}{DinoVision evidence archive},
and its \href{https://github.com/kvark/dinovision/tree/dc35cdf1c7c910cdd93c5b5362846842ae469a21}{source code}
is public too.

\section{Maintenance and Debugging}
\label{sec:productivity}

We did not measure developer effort, learnability, or maintenance time, and
we claim no quantitative productivity advantage. Some observations still
bear on it. Application code expresses tensor graphs and reuses checkpoints
across backends. One stack means one implementation to maintain, but
maintaining it takes WGSL, memory, synchronization, and numerical expertise.
A static compiler can fuse away or alias the values a developer wants to
inspect, so debugging may need a less optimized plan. \system{} can read
named intermediates, map graph operations to dispatches, locate the first
nonfinite value, and run the same kernels eagerly. These tools separate
rewrite, storage-reuse, and kernel bugs, although eager execution of the same
kernels is not an independent reference. Calibrated timestamps align CPU work
with GPU passes, while native tools such as Nsight Graphics remain necessary
for occupancy and stall analysis \cite{nvidia2026gputrace}. Deployment needs
no Python or vendor ML runtime, which kept the DinoVision integration within
one graphics stack.

\section{Related Work}

Pennycook et al.\ define and later revisit the portability metric used here
\cite{pennycook2016metric,pennycook2021revisiting}. Kokkos and RAJA express
portable parallelism and memory policy in C++ libraries
\cite{edwards2014kokkos,beckingsale2019raja}, and SYCL standardizes
single-source heterogeneous C++~\cite{khronos2020sycl}. We start instead from
graphics APIs and build a tensor compiler on top. Lin et al.\ measure
programming-model productivity through semantic divergence
\cite{lin2024productivity}; preparation time and executable size do not
replace that measure.

TVM, Glow, MLIR, and Triton established graph and kernel compilation for ML
\cite{chen2018tvm,rotem2018glow,lattner2021mlir,tillet2019triton}, and RAF
extends whole-graph compilation to training~\cite{yu2023raf}. TASO searches
verified graph substitutions \cite{jia2019taso}. TENSAT and Glenside apply
equality saturation to tensor programs
\cite{yang2021tensat,smith2021glenside}, building on egg
\cite{willsey2021egg}. \system{} uses egglog \cite{zhang2023egglog}, adds
matrix schedules to the same e-graph, and measures candidates instead of
trusting one cost model. Compile-time autotuning is itself established
practice \cite{chen2018tvm,tillet2019triton}.

Several systems already run ML through graphics APIs. IREE compiles MLIR
programs to Vulkan and Metal, and TinyIREE measures its footprint for
embedded inference \cite{liu2022tinyiree}. llama.cpp \cite{ggml2026llamacpp}
and ncnn \cite{tencent2026ncnn} run inference through Vulkan kernels, WebLLM
and LlamaWeb do so through WebGPU \cite{ruan2024webllm,levine2026llamaweb},
and ExecuTorch deploys exported PyTorch programs across mobile backends
\cite{nachin2026executorch}. TensorFlow.js trained models in the browser
\cite{smilkov2019tensorflowjs}, and memory-constrained on-device training
studies a complementary regime \cite{lin2022ondevice}. Burn is a broader Rust
framework with compute and graphics backends, autodiff, and fusion
\cite{simard2026burn}. Our contribution is a measured comparison of one
compact graphics-API stack for both training and inference against compiled
PyTorch across vendors, including its failures, preparation cost, and a
deployment. \inferena{} can drive several of these frameworks, but we compare
only against PyTorch, which supplies the mainstream vendor-specific training stacks in the
performance comparison.

\section{Threats to Validity}

\emph{Platforms.} A common PyTorch revision does not equalize vendor
libraries, drivers, host CPUs, or operating systems. The XPU accommodations
and MI300X MIOpen solver exclusion change the reference paths. MI300X also
requires experimental Mesa and AMDGPU patches, and MPS has no whole-phase
replay. Results apply to those recorded configurations.

\emph{Budgets.} The engines prepare under different policies and limits, so
we claim neither equal startup cost nor the fastest possible implementation.
The submitted search ablation used an older compiler and allowed submission
chunking. It does not supply a control arm for the present cohort.

\emph{Replication.} Three processes per condition do not characterize a
population of machines. CPU power management, cloud co-tenancy, thermals,
and the short timing window can all matter. Fresh processes start with empty
TorchInductor caches but keep whatever driver state the machine had. We
report warmed short-window latency rather than sustained throughput and
remove no outliers.

\emph{Numerics.} Strict f32 fixes width, not operation order. Native full
gradient fidelity, PyTorch's trajectory gate, and cross-engine snapshots
have different scopes (Section~\ref{sec:gates}); they do not establish
equivalent learning quality. PyTorch's fixed dtype choice and native search
also have different opportunities to retain a qualified implementation.
Relaxing a bound could change native kernel and tiling selection as well as
PyTorch eligibility. No tolerance-sensitivity study was collected, and
relabeling archived failures would not reconstruct one. Aggregates are
conditional on both engines passing; absent references are not speed wins.
The performance-portability metric deliberately mixes coverage with speed,
so its ranking inherits the numerical policy.

\emph{Scope.} The larger models run at batch one with short contexts and no
key/value cache. The timed step excludes optimizer updates and communication,
and there is no distributed training experiment. The diffusion U-Net is
reduced, Whisper lacks its decoder, and ResNet folds its normalization.
Experience with several vendors shaped this compiler, so the results do not
separate its architecture from the engineering effort behind it.

\section{Future Work}

The next experiments should isolate the effects of search budget, kernel
memo reuse, matrix features, and numerical bounds, with the same workload
and repeated timing of selected programs. Native trajectory checks would
close an important qualification asymmetry. B570 needs efficient qualified
rectangular kernels, while H100 needs matched-precision kernel and memory
analysis; enabling the features has not closed these gaps. MI300X requires
further driver validation and integration. Persistent megakernels could
move dependency scheduling onto the GPU, as MPK does for CUDA task graphs
\cite{cheng2026mpk}, subject to graphics-API forward-progress and
synchronization constraints.

\section{Conclusion}

One compiler and runtime qualifies all five core workloads under both
profiles on eleven GPUs, including integrated and mobile devices and a
compute-only MI300X with experimental driver patches. Seven platforms
provide replicated performance, with 246 independently qualified native
cells including larger models and 226 qualified paired comparisons.

Coverage does not imply speed parity. Core strict median time ratios are
1.35 for inference and 1.61 for training; accelerated ratios are 2.06 and
2.21 over different qualified subsets. MI300X's strict training ratio
narrows to 1.65 at 1.7B, whereas H100's grows to 3.79. Workgroup matrix
operations are selected on NVIDIA, but BF16 and rectangular support do not
automatically produce winning programs. Numerical policy, reference coverage,
and M3 timing variation constrain interpretation. Graphics APIs provide a
viable common compute interface; competitive performance still requires
compiler, runtime, and driver engineering.
