\begin{abstract}
Graphics application programming interfaces (APIs) offer a common execution
path for machine learning across consumer and edge graphics processing
units (GPUs). Meganeura is a compact native
compiler and runtime that lowers tensor graphs and automatic
differentiation to Vulkan and Metal kernels. We evaluate five workloads
on seven GPU-reference configurations, including an NVIDIA H100 and Windows, with one PyTorch
source revision, compiled references, and independently qualified CUDA, HIP,
and XPU graph replay wherever those APIs are available.
Meganeura always performs bounded kernel search during compilation, and
strict arithmetic permits native-f32 cooperative matrices.
All 222 paired process runs pass the numerical gates, including replicated
360-million- and 1.7-billion-parameter H100 extensions.
Across seven complete GPU-reference configurations, median strict
32-bit floating-point inference and training times are $1.83\times$ and
$2.47\times$ PyTorch's. Search covers every eligible class in 606 of 624
native sessions; preparation cost and performance gains remain workload-dependent.
Meganeura executes on an Intel integrated GPU without a usable PyTorch
GPU path; a separate AMD MI300X attempt
instead exposes missing Vulkan driver support.
Graphics APIs broaden deployment options, while vendor compute stacks
retain a performance advantage on most workloads. Validation, preparation
costs, and host/GPU profiles help explain where this approach is useful
and what limits its reach into high-performance computing (HPC).
\end{abstract}

\section{Introduction}

Performance-portability layers such as Kokkos, RAJA, and SYCL let one
program target heterogeneous hardware
\cite{edwards2014kokkos,beckingsale2019raja,khronos2020sycl}.
Graphics APIs suggest a complementary substrate for machine learning
(ML): Vulkan exposes cross-vendor graphics and compute, while Metal
serves Apple platforms \cite{khronos2026vulkan,apple2026metal}.
An application already using these APIs can share its driver, resources,
and execution queue with a tensor runtime. We investigate the performance
and hardware coverage of that deployment choice.

We study \system{}, a compact native compiler and runtime that lowers a
typed tensor graph and its differentiated training graph to specialized
compute kernels. Blade supplies the Vulkan/Metal abstraction
\cite{malyshau2026barriers}. Model construction, graph transformations,
automatic differentiation, checkpoint semantics, and the runtime interface
remain common across devices; deployed applications require neither Python
nor a vendor ML runtime. Training and inference use the same compiler.
Optional empirical kernel selection runs inside session construction,
so deployment-time compilation can also perform bounded measurement.

The evaluation compares \system{} with PyTorch
\cite{paszke2019pytorch} at one source commit across CUDA, ROCm, XPU, MPS,
and CPU-oracle wheels. Every timed reference uses default compilation. CUDA, HIP, and
XPU execute explicitly captured, numerically qualified whole-phase graphs;
MPS has no equivalent public replay interface. Native empirical selection
is always enabled, independently of the reference's compiler mode.
We measure the performance available after bounded preparation, including
the cost of preparing each workload.

Performance, portability, and productivity (P3) raise three distinct questions.
\emph{Performance} is elapsed
time against a declared valid reference, with arithmetic permissions and
preparation policy stated. \emph{Portability} includes whether that policy
can execute at all: PyTorch has no usable GPU path on the evaluated Intel
RPL-U system, whereas \system{} has no validated Vulkan path on the
attempted MI300X. \emph{Deployment efficiency} includes specialization
wait and runtime closure. We discuss debugging and maintenance burdens
qualitatively; these operational measurements are not a programmer-productivity
score \cite{lin2024productivity}.

Our contributions are:
\begin{itemize}
  \item A correctness-gated comparison of one native graphics-API ML
        compiler and runtime across eight device configurations, with a common PyTorch
        revision, qualified replay across three backend APIs, and explicit
        support boundaries.
  \item A measured preparation/performance tradeoff with automatic kernel
        selection inside \system{}'s compilation, including actual search
        coverage, numerical rejections, and specialization costs.
  \item Separately pinned evidence distinguishing host command recording
        from representative GPU bottlenecks, together with a replicated
        H100 model-size extension and concrete improvement experiments.
\end{itemize}

An arithmetic contract (Section~\ref{sec:contracts}) specifies permitted
numerical fast paths. Each device--workload--contract--policy comparison
is validated before its timings are admitted. Graphics-only qualification
remains visible without entering the GPU performance aggregate.
This study includes datacenter hardware and up to 1.7-billion-parameter
models, but not production-scale large language model (LLM) training, optimizer updates,
distributed execution, or scientific simulation workloads.
The companion technical report develops the compiler and system design
in greater detail \cite{malyshau2026meganeura}.

\system{} executes a typed static tensor graph (Figure~\ref{fig:pipeline}).
Native builders and importers for Open Neural Network Exchange (ONNX)
and Neural Network Exchange Format (NNEF) construct the graph.
A deterministic greedy rewriter optimizes it; training adds reverse-mode
differentiation and, when requested by the application, a stochastic
gradient descent (SGD) or Adam update.
The benchmark measures forward, loss, and backward only.
An equality-saturation mode also exists, but is outside this comparison.

Code generation uses a small set of reusable kernel families:
pointwise expressions, reductions, general matrix multiplication (GEMM), convolutions and
their derivatives, and tiled attention. Shape, device capabilities,
and precision policy determine legal implementations and workgroup
geometry. The generated WebGPU Shading Language (WGSL) is validated
by Naga \cite{w3c2026wgsl}; Blade lowers it for native Vulkan/Metal.
Sharing Naga with wgpu does not mean using the wgpu runtime or executing
in a browser.

The compiler fixes a dispatch sequence and lifetime-based buffer reuse.
Each step records and submits that plan without graph rediscovery or
per-step tensor allocation; host command recording and synchronization
remain. It does not replay a native CUDA Graph.
The reference therefore receives its native command-graph replay path,
rather than paying an avoidable per-step Python submission cost.

With empirical selection enabled, session construction generates legal
alternatives, qualifies their numerical results on private scratch
buffers, measures successful candidates, and retains the incumbent when
none qualifies or improves performance. The measured implementation searches
a bounded subset of matrix tiles and shape-specialized convolution
implementations, including alternative reduction staging.
The measured per-session search budget is 60 seconds, without a class-count
cutoff, and at most 1\,GiB of scratch storage, also constrained by available
device memory. The time limit is soft: it cannot preempt
an in-flight driver compilation or GPU qualification.
Search follows greedy graph rewriting. Graph compilation and measured
kernel selection share one deployment step, although graph representations
and some kernel families remain outside the search
(Section~\ref{sec:search}).

\section{Methodology}
\label{sec:method}

\inferena{}, the open-source cross-framework harness, constructs matched
workloads, alternates engine order, synchronizes timing boundaries,
and records raw samples, outputs, gradient norms, revisions, and
environment metadata.\footnote{\href{https://github.com/kvark/inferena/tree/fa5a04e1c1b38405cfa371a27c5dcef1319835d5}{Inferena source, revision \code{fa5a04e1}}.}
It supplies kernels to neither engine.

\subsection{Revisions and reference conditions}
\label{sec:reference-policy}

Every supplied campaign uses \inferena{} \code{fa5a04e1} and
\system{} \code{428fc2d2}, with Blade \code{f6f2729}.
All wheels report PyTorch 2.13.0 at source
commit \code{cf30153}, with Python 3.13.13. NVIDIA uses
\code{+cu130}, AMD \code{+rocm7.2}, Arc \code{+xpu}, Apple the MPS
wheel. RPL-U qualification uses \code{+cpu} as a correctness oracle only.
Checkpoint revisions and hashes are recorded in the manifests.
Driver, host, and backend-library differences remain part of the platform;
a common PyTorch revision does not make those implementations identical.

Arithmetic and preparation are separate axes. Both arithmetic contracts
pair tuned Meganeura with default-compiled PyTorch.
We choose this preparation policy because max-autotune was costly and
unreliable during bring-up: an H100 pilot spent 170.3 minutes compiling
30 searched pairs versus 14.0 minutes for the same default/replay matrix
(Section~\ref{sec:productivity}), while Radeon searches failed and Arc's first
searched ResNet qualification did not finish within an hour
(Section~\ref{sec:availability}).
Default compilation gives every backend the same practical reference policy.

PyTorch's \code{max-autotune}, GEMM/pointwise search and coordinate-descent
options are disabled; default compiler and vendor-library heuristics still
apply \cite{pytorch2026compile}. A supervisor enforces a 120-second
compilation deadline covering the first forward, backward, and minimal-shape
specializations, terminating compiler descendants on failure.
Model loading, graph capture, and research validation are outside that deadline.
Meganeura uses the per-session search ceiling above. These limits bound
preparation differently; this is neither an equal-budget contest nor a
comparison with the fastest PyTorch configuration obtainable after a long search.

CUDA and ROCm use \code{torch.cuda.CUDAGraph}; ROCm maps that interface
to HIP graphs. Intel uses \code{torch.xpu.XPUGraph}
\cite{pytorch2026hip,pytorch2026xpugraph}.
Inductor's internal \code{triton.cudagraphs} mechanism is disabled so the
explicit capture is the sole replay owner. XPU uses the public math
scaled-dot-product-attention (SDPA) backend to accommodate graph capture;
the setting and a qualified embedding-backward workaround are recorded
(Section~\ref{sec:availability}). Other backends retain automatic SDPA selection.
MPS also compiles all requested
phases. MPS's Inductor path is exercised \cite{pytorch2026mpssource}, but
the pinned MPS API offers no equivalent public whole-phase replay interface.
MPSGraph execution is not CUDA Graph capture. No failed compiled or
captured condition may silently substitute eager or CPU execution.

\subsection{Workloads and timing}

The five principal workloads are SmolLM2-135M (decoder-only transformer)
\cite{benallal2025smollm2},
the SmolVLA action expert (99.85M parameters)
\cite{shukor2025smolvla}, a scaled Stable Diffusion 1.x U-Net
(10.93M, not checkpoint-compatible with SD~1.5)
\cite{rombach2022ldm}, ResNet-50 at batch four
\cite{he2016resnet}, and the Whisper-tiny encoder (8.21M)
\cite{radford2022whisper}. Both runners use the same shapes,
deterministic inputs, scalar objective, and canonical parameter names.
The additional H100 campaign requests SmolLM2-360M and SmolLM2-1.7B.

Three phases are timed: full no-gradient forward, minimal-shape forward,
and forward--loss--backward (F+L+B), without an optimizer update.
SmolLM2 uses batch one, 128-token prefill and one stateless token.
There is no key/value cache; the latter is not an autoregressive serving
benchmark. Whisper's full and minimal shapes coincide.
Each phase has five untimed warmups and 20 synchronized host-wall samples.
Input loading and output/gradient readback occur outside the timing
interval. Buffers are initialized before execution; the retained planner
memory counts do not prove physical residency of every binding.

Each condition runs in three fresh process pairs, with alternating
engine order and rotated condition order. We report the median of the
three within-process medians, and retain their range and all samples.
Twenty calls in one process are not twenty independent replicates.
An interrupted campaign retains its completed pairs with their actual
replicate counts, but does not enter the complete-cohort aggregates.
Unreached runs are unmeasured, not framework failures.

\subsection{Arithmetic contracts}
\label{sec:contracts}

Strict f32 disables TensorFloat-32 (TF32) in PyTorch and reduced-input
cooperative-matrix paths in \system{}. Tensor storage,
accumulation, and outputs remain f32.
Qualified f32-input/f32-accumulate cooperative tiles are allowed: this
contract preserves arithmetic width, not reduction order. Apple M3 exposes
such tiles and records strict cooperative dispatches in all five workloads;
the measured Vulkan devices expose none through this stack.
The accelerated contract permits PyTorch's TF32 paths and
\system{}'s supported cooperative implementations, including
f16-input/f32-accumulate forward matrix, convolution, and attention work.
Derivative regions retain the full-precision policy.
The permissions are not identical numerical formats, and a device may
expose no implementation that engages them.
No quantization or persistent f16 tensor storage is enabled.

\subsection{Independent numerical gates}

Cross-engine forward validation checks shape, relative L2 error below
1\% over 256 evenly spaced output samples, and relative scalar-loss
error below 1\%. Backward validation additionally checks canonical
parameter sets, total-gradient-norm error, and relative L2 error of the
per-parameter norm vector.
Strict runs require both gradient errors below 5\%.
The frozen accelerated replication rule requires each error below 10\%
and the median of three process errors below 5\%, accommodating permitted
nondeterminism without accepting an unbounded outlier.
Every pair in this cohort individually stays below 5\%; the largest
parameter-norm-vector error is 3.30\%, sampled-output error 0.628\%,
and scalar-loss error 0.0861\%.
Norm checks can miss sign or elementwise errors, and sampled outputs
can miss localized errors.

CUDA, HIP, and XPU replay have a separate, full-element gate against
uncaptured PyTorch.
Preparation, warmup, capture, and execution share one dedicated stream.
Every participating output and gradient element is checked over consecutive
uncaptured calls and two consecutive replays.
Accelerated training uses eight uncaptured repeats; other phases use two.
Each output and loss tensor must satisfy both a maximum-error and a
root-mean-square (RMS) error bound: $10^{-6}+10^{-4}r$, where $r$ is the
corresponding reference maximum or RMS. This avoids a near-zero-sensitive pointwise
relative test without fitting tolerances to observed repeats.
Strict gradients use those bounds per parameter and over the whole gradient;
accelerated gradients use whole-gradient bounds with coefficient $10^{-2}$.
Ordinary repeatability and replay errors are recorded separately against
the first uncaptured result.
Capture or validation failures abort the requested condition; no eager
timing replaces a failed graph run.
The retained reports establish that this qualification ran, but do not
contain all tensor elements for independent offline revalidation.

\subsection{Performance under bounded preparation}

Across the seven GPU-reference configurations, strict median ratios are
1.83 for inference, 1.28 for minimal shapes, and 2.47 for training.
Nominal win counts are 7/35, 10/35, and 3/35 respectively.
With accelerated arithmetic, the corresponding median ratios are
2.12, 1.61, and 2.91, with 6/35, 9/35, and 4/35 nominal wins.
These populations describe the declared available configurations, not
equal accelerator capabilities or statistically established win counts.

Meganeura is most competitive on the Radeon devices. Strict RX~7900~XT SmolLM2
and SmolVLA inference ratios are 0.89 and 0.76; their minimal shapes are
0.32 and 0.34. SmolVLA training is faster at 0.70.
Radeon~780M wins three inference and two training comparisons in strict
mode, while convolution workloads remain its principal deficits.
Arc~B570's compiled, replayed reference wins every phase in both contracts:
strict full-inference ratios span 2.32--4.31 and training 3.46--5.98.
M3 uses native-f32 cooperative matrices and wins diffusion inference
(0.46) and three minimal shapes, but none of the five training comparisons.

On RTX~5070, strict ResNet inference is faster at 0.87, while other
full-inference ratios span 1.24--2.72 and training spans 2.16--2.83.
Windows RTX~3050 completes all three replicates with qualified replay;
strict inference is 1.14--2.12 times PyTorch's and training 1.90--2.57.
Its one-token SmolLM2 result is close at 1.02.
H100 is an out-of-development-platform reference: no H100-specific
profiling or optimization preceded collection. It tests transfer to
datacenter hardware, not the ceiling of an H100-tuned implementation.
Strict training ratios span 2.59--4.03; accelerated ratios span 4.07--13.04.
Accelerated ResNet has the largest gap. These engine/driver results
cannot, by themselves, attribute that difference to barriers or one
instruction family.

The widest native process range is M3 strict SmolVLA training:
52.84--109.03\,ms around a 70.40\,ms median. H100 strict ResNet inference
ranges 4.26--6.55\,ms around 4.58\,ms.
Three short runs cannot establish a stable optimum, especially for the
small differences on M3.

Of 624 sessions in the paired GPU campaigns, 606 visit every eligible class,

The legal domain includes scalar-f32 matrix implementations, supported
native-f32 cooperative alternatives, and shape/staging choices for
convolution forward and derivatives. It does not include every generated
kernel: matrix--vector multiplication (GEMV), reduced-input cooperative variants,
complex fused prologues, and graph representation changes remain outside
the implemented search.
M3 records 2,150 cooperative dispatch instances across the 15 strict
processes; their presence is verified, but this cohort contains no
cooperative-off ablation from which to infer a causal speedup.

A separately retained H100 pilot provides an actual search-off/on control
at Meganeura \code{75dfe901} and Inferena \code{efb1e520}, with three process
replicates and a narrower two-second native search. Strict 135M prefill
falls 13.26$\rightarrow$9.74\,ms ($1.36\times$), and training
52.41$\rightarrow$42.72\,ms ($1.23\times$).
This establishes that measured kernel choice can improve execution
without model-specific code. It is not an ablation of the current
60-second policy or its additional native-f32 permissions.
The pilot's preparation costs are discussed in Section~\ref{sec:productivity};
its records are separate from the primary tables and aggregates.

\subsection{Conditional performance portability}

\begin{table}[t]
\caption{Strict scores over seven shared GPU-reference configurations.}
\label{tab:pp}
\centering
\small
\setlength{\tabcolsep}{4pt}
\input{tables/portability}
\end{table}

For workload $a$, phase $q$, implementation $i$, and declared machine
set $S$, application efficiency is
$e_{i,a,q}(p)=t_{\mathrm{best\ valid},a,q}(p)/t_{i,a,q}(p)$.
We use the Pennycook metric \cite{pennycook2016metric,pennycook2021revisiting}:
\begin{equation}
P_{i,a,q}=\begin{cases}
|S|\big/\sum_{p\in S}1/e_{i,a,q}(p),&\text{valid on every }p,\\
0,&\text{otherwise.}
\end{cases}
\end{equation}
Best means the faster valid result of these two engines under the declared
policies. Table~\ref{tab:pp} uses the same seven GPU-reference systems for
every workload and phase. Its final row is the arithmetic mean of the five
workload scores, not a new harmonic aggregate over applications.
Meganeura/PyTorch means are 0.51/0.93 for inference, 0.60/0.85 for minimal
shapes, and 0.39/0.98 for training.

This is explicitly conditional on shared GPU support. It excludes the RPL-U
reference, additional H100 model sizes, and MI300X availability attempt;
it cannot stand in for universal support.
If support is required across every attempted GPU, both stacks have a
known hole and hence a zero score: PyTorch on RPL-U, Meganeura on MI300X.
The availability results below are therefore as necessary as the
conditional performance scores.

\section{Edge Deployment Beyond the Matrix}
\label{sec:edge}

The matched matrix contains no Android reference, so Android contributes no
performance-portability score. A separately versioned physical deployment
tests the stack in an interactive edge application. DinoVision reconstructs
the headset cameras' live images from features computed by a vision encoder
(DINOv3~\cite{simeoni2025dinov3}). Figure~\ref{fig:dinovision} shows the
reconstructed view displayed on the headset. \system{} trains
a 2.01-million-parameter decoder on a host GPU, saves its parameters, and
loads them into a joined batch-one encoder/decoder graph on a Quest~3S. The
deployed graph performs 2.359 billion multiply--accumulates and runs
through the same graph representation,
compiler, memory planner, checkpoint format, and Blade runtime. Two
asynchronous eye sessions share Blade's Vulkan context and queue with the
OpenXR renderer.
This shared context also makes hybrid applications straightforward:
games and interactive visualizations can combine rendering and ML without
introducing a separate vendor ML context. Resource sharing and queue
scheduling become application-level choices within one graphics stack.

\begin{figure}[t]
  \centering
  \includegraphics[width=0.73\columnwidth]{../figures/dinovision-quest3s.jpg}
  \caption{Quest~3S casting capture of DinoVision's live RGB
  reconstruction. This documents physical deployment; it is not a visual
  quality or capture-to-photon benchmark.}
  \label{fig:dinovision}
\end{figure}

We ask two separate questions: does the deployed graph reproduce the host
output, and how does its GPU work affect the renderer sharing the queue?
The first has an independent host/device gate. For one fixed public
RGB frame and identical weights, preprocessed patches are bit-exact; Quest
encoder output has relative $L_2=0.001059$ and the final reconstruction has
relative $L_2=0.000457$ against the host. An isolated synchronized run takes
96.78\,ms as one submission chunk. Splitting the ordered dispatch plan into
two chunks costs 4.1\% in isolation, but under a 90-second live stereo sweep
it raises application render submissions by 18.8\%, raises the lower-eye
update rate by 8.7\%, and reduces median worker latency by 20.2\%. Larger
chunk counts regress non-monotonically. The best schedule here differs
between isolated inference and a shared rendering queue. A common graphics
stack lets the application make that choice without a second GPU runtime.

This case study establishes deployment closure and queue co-tenancy, not
on-device training or speedup over PyTorch on Android. Its weights, raw
samples, manifests, and full-resolution media are available in the public
\href{https://huggingface.co/mad-bot/dinovision}{DinoVision evidence
archive}; its \href{https://github.com/kvark/dinovision}{source code} is
public as well.

\section{Locating the Gaps}
\label{sec:gaps}

Finer attribution uses separate diagnostic runs, not replacements for
the unprofiled cohort. The RTX~5070 ResNet-50 study below uses Meganeura
\code{75dfe901}, Blade \code{f6f2729}, strict f32, batch four, two-second
native search, and PyTorch max-autotune. These diagnostic policies and
the native revision differ from the primary cohort; their profiles motivate
engineering changes, not an exact attribution of its remaining gap.
Nsight Systems 2026.4.1 records the ordinary grouped Vulkan
schedule and qualified CUDA Graph nodes; Nsight Graphics 2026.3.1 supplies
hardware counters. Each diagnostic uses five warmups and three measured
calls in one process, not three independent process replicates.
Meganeura's calibrated timestamps align CPU and GPU events; optional
per-dispatch profiling changes the pass schedule and is charged separately.

The small output leaves most SMs without a workgroup to execute.

A short grouped Nsight Graphics capture corroborates underutilization:
one complete 40.64\,ms training interval reaches 32.1\% of peak SM
throughput and 6.1\% of peak device-memory throughput. These counters
have different denominators; low memory bandwidth does not rule out
memory latency. The 1.92\% peak-normalized workgroup-barrier warp counter
is \emph{not} Vulkan resource-barrier wall cost
\cite{nvidia2026gputrace}.
The Graphics-only runner shares a context and adds a phase trigger;
its controls preserve the retained outputs and gradient norms.
Source, instrumentation boundaries, and commands are retained on the
diagnostic revision.\footnote{\href{https://github.com/kvark/inferena/blob/3f8f994ce02aaf89ec5167d601403dc314b08e93/ANALYSIS-2026-09-13.md}{RTX~5070 diagnostic, revision \code{3f8f994c}}.}

The diagnostic's ordinary production-binary
log run visits only five of 71 eligible training classes before its
2.005\,s soft deadline. The small-output family is never visited:
priority is estimated arithmetic volume, not measured execution time.
Selected shape-specialized convolution variants are present elsewhere.
The primary cohort broadens the time/scratch budgets and removes the
eight-class cap; all RTX~5070 and H100 classes are visited.
Prioritizing measured expensive classes remains useful on deadline-limited
devices. Small-output,
long-reduction kernels also need more parallel decompositions;
past split-reduction candidates failed numerical qualification, so they
remain research targets rather than ready optimizations.

A separately pinned resident-parameter study (Inferena \code{111579d})
provides complementary transformer evidence: native 1.7B prefill spends
52.67\,ms in its grouped GPU span versus 27.91\,ms of PyTorch kernel
intervals. A longer 135M token control separates a host cost directly:
GPU time stays near 1.88\,ms while command-recording thread CPU time
grows from about 0.59 to 1.44--1.48\,ms as the host downclocks toward
800\,MHz. Elapsed recording and thread CPU time agree, making simple
descheduling an inadequate explanation.
Low CPU demand can make downclocking a reasonable power-management
response, rather than a system malfunction. Here it nevertheless raises
command-recording cost and token latency; energy savings were not measured.
This explains a short-window latency sensitivity; it is not a GPU-barrier
measurement or a reason to discard slower final-cohort samples.
\footnote{\href{https://github.com/kvark/inferena/blob/89b2d3e71d9a8cb9d22c6ab0800ca4a43e3ba3a7/ANALYSIS.md}{Transformer diagnostic, revision \code{89b2d3e7}}.}

Profile-guided engineering already contributes a production improvement.
Immutable convolution indexing and alternative staging are now ordinary
tuning candidates, rather than an experimental global override.
Separate six-pair qualification on synthetic batch-one ResNet-50 reduces
F+L+B from 21.133 to 17.729\,ms on RTX~5070 ($1.19\times$) and
35.880 to 31.651\,ms on B570 ($1.13\times$), with about two seconds
of training-session search and unchanged numerical checks.
These are separately pinned qualification workloads, not the cohort's
batch-four timing claims. The production candidate integration is
included in the cohort, with search enabled on B570 as well as NVIDIA.

On token shapes, qualified Graphics samples concentrate in three
GEMV families, especially residual-add
and root-mean-square-normalization (RMSNorm) fused variants.
Changing the residual-add workgroup width and avoiding a packed-weight
copy improve separate resident-model experiments; the current production
tuner does not search those choices.
These results identify workgroup geometry and graph representation as
reusable search dimensions.

Matrix instruction access may also contribute to the accelerated H100 gap.
Hopper's CUDA/PTX path exposes asynchronous matrix operations across a
128-thread warpgroup (\code{wgmma}), with explicit issue and completion
control \cite{nvidia2026wgmma}. The measured Blade/Naga Vulkan path accepts
only subgroup-scope $8\times8$ or $16\times16$ tiles
\cite{blade2026matrices}; it does not expose that programming model.
Vulkan's vendor extension \code{VK\_NV\_cooperative\_matrix2} adds workgroup
scope and more flexible dimensions, but this stack does not use it
\cite{khronos2024cooperative2}. This is a possible implementation/capability
gap. Determining its contribution requires inspecting matched-precision
machine code on H100; these measurements establish neither a specific
instruction deficit nor a fundamental Vulkan limit.

None of these measurements establishes a removable Vulkan-barrier
percentage. Workgroup barriers inside shaders, resource dependencies
between dispatches, host submission, and waiting are different mechanisms.
In particular, wall time minus summed kernel time is not barrier cost:
execution overlaps, and instrumentation changes the schedule.
Our companion synchronization study demonstrates the sensitivity of
graphics abstractions to barrier policy \cite{malyshau2026barriers},
but predates the present resource tracking.
Per-kernel attribution on H100, AMD, and Intel remains incomplete;
the final cohort establishes their gaps, not a universal causal breakdown.

\subsection{Preparation as a deployment budget}

Native \code{compile\_s} covers graph construction, optimization,
autodiff, and native pipeline creation across the requested sessions,
including empirical search. Most models construct three sessions;
Whisper reuses one inference session for its two timing shapes.
PyTorch \code{compile\_s} includes compilation and the first
specializations/executions of forward, backward, and minimal shapes,
including on MPS.
Graph preparation and full-tensor qualification are recorded separately;
model loading, cross-engine validation, and other process startup
are outside these fields. These are declared preparation components,
not application time to first answer.

Preparation cost varies substantially by workload.

The H100 pilot in Section~\ref{sec:search} measures the cost of max-autotune.
Over 30 searched
pairs (five models, both contracts, three replicates), PyTorch
compilation/first execution totals 170.3 minutes, versus 114.7 seconds
for that pilot's two-second native search policy. Default PyTorch
compilation over the equivalent 30 replayed pairs totals 14.0 minutes.
For strict ResNet, max-autotune improves inference $1.28\times$ while
compilation rises 14.09$\rightarrow$601.27\,s.
The 170.3-minute total covers the entire searched matrix, not one model.
It motivates the primary cohort's default-compilation policy on every backend.

Cheap shader translation makes deployment-time search practical, but is
only one stage. A separate RTX~5070 compiler study measures median WGSL
parse calls of 141--172\,$\mu$s on three workloads; native driver
pipeline creation accounts for hundreds of milliseconds in session
preparation. A matched-domain f32 GEMM microstudy, after compiler warmup
and with fresh private disk caches, measures 30.8--31.2\,ms to prepare
a native candidate versus 100.4--166.6\,ms for Triton.
Both include machine-code preparation; allocation and execution are
outside these intervals. This is a few-fold candidate-preparation
advantage once native driver work is included. Sources and commands are
retained with the compiler-stage experiments.\footnote{\href{https://github.com/kvark/meganeura/blob/428fc2d2322229e5338f5d80a10d700340d593cd/docs/experiments.md}{Compiler experiments, revision \code{428fc2d2}}.}

Compile-time autotuning is established practice
\cite{chen2018tvm,tillet2019triton}. The architectural opportunity here is
to combine graph compilation and bounded measurement inside a compact,
portable deployment runtime. The primary cohort measures that integration
everywhere, including platforms on which the reference's searched policy
proved impractical during bring-up. Matching the word \emph{autotune}
does not match deployment budgets. An equal-deadline comparison would
additionally enforce the same end-to-end preparation boundary; this
study instead declares a native per-session search ceiling and a reference
whole-specialization deadline, and reports their actual costs.

MI300X exposes a different boundary: driver availability for a
compute-focused accelerator. PyTorch/ROCm runs strict 135M on the attempted

the required tensor computation is intrinsically unsuitable for Vulkan.
Supporting a compute-focused device is a plausible driver-engineering
direction; neither its effort nor a working ML path is established by
this bring-up report. The currently usable deployment surface remains
narrower than the hardware's potential.

\subsection{Application authors and backend maintainers}

Application authors express tensor graphs and reuse checkpoints across
backends. Backend maintainers still need expertise in WGSL, memory,
synchronization, and numerical behavior. Sharing the graphics stack
concentrates this specialist work; it does not eliminate it.
Eager PyTorch offers immediate tensor inspection, Python execution,
autograd hooks, and anomaly detection.
A static compiler can fuse away values or alias their storage, so
debugging may require preserved intermediates or a less optimized plan.
Meganeura provides named intermediate reads, graph-to-dispatch provenance,
first-nonfinite attribution, and same-kernel eager evaluation.
These help distinguish graph transformations, storage reuse, and kernel
errors. The same-kernel path is a diagnostic, not an independent numerical oracle.

Portable timestamp/provenance traces connect CPU work with GPU passes;
native tools remain necessary for instruction, occupancy, and stall analysis.
The XPU compatibility probes illustrate why such observability matters
even when broad regression gates pass.
We did not measure developer-hours, learnability, maintenance effort, or
equivalent independent ports, and claim no quantitative productivity advantage.

An earlier, separately versioned Linux deployment audit found a
12.8\,MiB stripped native benchmark runner, versus 1.75\,GiB for the
PyTorch/Triton packages and 4.66\,GiB for the recursive CUDA runtime
dependency closure \cite{malyshau2026meganeura}.
The audit excludes weights, Python itself, ordinary OS libraries, and
the GPU driver. It is historical deployment evidence, not a new footprint
measurement of this cohort or a feature-equivalence comparison.
Section~\ref{sec:edge} supplies the complementary physical application check.

\section{Related Work}

Pennycook et al.\ define and later revisit the portability metric and
platform-set discipline used here
\cite{pennycook2016metric,pennycook2021revisiting}. Kokkos and RAJA encode
portable parallelism and memory policy in C++ libraries
\cite{edwards2014kokkos,beckingsale2019raja}; SYCL standardizes a
single-source heterogeneous C++ model~\cite{khronos2020sycl}. This study
instead fixes graphics APIs as the execution substrate and asks what a
domain compiler can recover. Lin et al.'s semantic-divergence metric also
motivates our restraint around the word productivity: our operational
measurements are not a substitute for their programmer-facing method
\cite{lin2024productivity}.

TVM, Glow, MLIR, and Triton established graph and kernel compilation for ML
\cite{chen2018tvm,rotem2018glow,lattner2021mlir,tillet2019triton}; RAF
extends whole-graph compilation to training~\cite{yu2023raf}. Burn~0.21 is a
broader Rust analogue, not a like-for-like compactness baseline: its documented
GPU targets span CUDA, ROCm, Metal, Vulkan, WebGPU, and LibTorch, with CubeCL,
Flex, and LibTorch CPU paths and decorators for autodiff, fusion, routing, and
remote execution~\cite{simard2026burn}. TensorFlow.js demonstrated
browser-resident training and inference~\cite{smilkov2019tensorflowjs}, and
systems for memory-constrained on-device training study a complementary
resource regime~\cite{lin2022ondevice}. Portable Rust autodiff is not the
novelty claimed here. The contribution is a frozen, validity-gated comparison
of one compact native graphics path across discrete, integrated, and
datacenter devices, coupled to profiles and deployment evidence.
\inferena{} was built to compare such frameworks, including Rust-originating
systems such as Burn, Candle, Luminal, and Meganeura. This paper selects
PyTorch as its reference rather than claiming results for every runner
available in that harness.

TinyIREE treats artifact and runtime footprint as first-class deployment
results for embedded inference~\cite{liu2022tinyiree}; ExecuTorch deploys
exported PyTorch programs across mobile backends at scale
\cite{nachin2026executorch}. WebLLM and LlamaWeb demonstrate browser
graphics-API inference performance
\cite{ruan2024webllm,levine2026llamaweb}. \system{} is narrower in framework
breadth, but carries the backward pass, optimizer, and checkpoint through a
native Vulkan/Metal stack. The companion technical report gives the full
system and compiler account~\cite{malyshau2026meganeura}; the Blade study
isolates synchronization in the underlying graphics abstraction
\cite{malyshau2026barriers}.

\section{Threats to Validity}

A common PyTorch source revision does not equalize vendor libraries,
drivers, host CPUs, operating systems, or permitted fast paths.
All primary references compile; CUDA/HIP/XPU use qualified replay, while
MPS has no equivalent public whole-phase API. XPU's recorded embedding
and math-attention accommodations are not an unmodified stock execution path.
The RPL-U qualification, additional H100 models, and MI300X report
cannot be pooled into the seven-system, five-workload GPU aggregate.
Conditional scores would overstate universal portability if support holes
were omitted.

Every native session enables search and permits legal native-f32 tiles
in strict mode, but coverage is bounded by the implemented domain,
memory availability, and soft time limit. The cohort has no search-off
or cooperative-off arm at its final revision. It therefore measures
deployable policies, not an isolated causal effect of tuning or
cooperative matrices. Native per-session and reference compilation
budgets have different boundaries; neither identical startup cost nor
the fastest possible implementation is claimed.

The larger models have three processes under both contracts, but do not
establish production LLM scaling: batch and sequence length remain small,
decoding has no cache, and training excludes optimizer state and distributed
communication. The diffusion graph is reduced, Whisper omits its decoder,
and ResNet uses inference-folded normalization.

Fresh processes have empty private TorchInductor/Triton caches, while
persistent driver and vendor-library state remains as found.
Alternating engine order mitigates rather than removes history dependence.
Preparation results describe installed systems, not independent first-use
cold starts. Disabling max-autotune does not clear a lower-level algorithm
choice established by earlier activity.

Three process replicates do not characterize a platform population.
CPU power policy, cloud co-tenancy, thermals, and timing-window length can
affect results. Process ranges are retained, including substantial M3
variation. Separate longer-warmup experiments expose host clock sensitivity;
the fixed 5/20 protocol measures warmed short-window latency, not guaranteed
sustained throughput. No outlier was removed to improve a ratio, and the
data do not separate tuning-choice variation from changing machine state.

Strict f32 constrains permissions, not operation order or bitwise identity.
Cross-engine sampled outputs and gradient norms can miss localized or sign
errors. Full-element replay qualification checks PyTorch against itself;
it does not turn the cross-engine gate into an elementwise gradient
comparison. All 222 GPU pairs and 30 RPL-U qualification processes individually
pass the 5\% gradient bound as well
as their required three-process rule. Replay's fixed tensor maximum/RMS
bounds and their coefficients are explicit; pointwise mismatch counts are
diagnostics, not a second acceptance rule.

Planner allocation sizes, allocator reservations, and process/driver
accounting have different meanings. A host-visible Vulkan allocation can
also occupy device memory; the planner's device-local category does not
prove physical heap placement. The final H100 extension is not a controlled
placement or PCIe study. Missing process-memory telemetry does not establish
a memory saving.

Development profiles, the H100 preparation pilot, and optimization ablations
carry separate revisions or policies and sometimes resident-parameter
controls. They explain representative mechanisms and remedies, not every
final-cohort gap. Work on several vendors informed this compiler; the
experiment does not isolate general architecture from accumulated engineering.
Nor do footprint and preparation metrics measure programmer productivity.

\section{Future Work}

Beyond kernel optimization, two directions test the generality of this
design. Neural accelerators would require a backend that represents their
operator, layout, and precision constraints; Vulkan/Metal GPU support does
not itself expose these devices. Graph partitioning could retain unsupported
operations on the GPU, but transfer and synchronization costs, numerical
qualification, and observability must enter the placement decision. A useful
extension should preserve one graph interface without promising identical
hardware capabilities.

Persistent megakernels could move dependency scheduling onto the device,
reducing dispatch boundaries and some intermediate memory traffic. MPK
demonstrates automatic tensor-program lowering to persistent CUDA task
graphs~\cite{cheng2026mpk}. Applying this idea through graphics APIs raises
different portability questions: workgroup forward progress, residency,
cross-workgroup synchronization, and register pressure. A bounded search
could choose profitable regions while retaining the ordinary multi-kernel
schedule as a qualified baseline. Neither direction is an implemented or
measured capability of the present system.

\section{Conclusion}

A single Vulkan/Metal compiler and runtime executes matched ML inference
and backward workloads across heterogeneous consumer systems and H100,
including Windows and an Intel GPU lacking a usable PyTorch GPU path.
All 222 paired GPU processes validate at common source revisions. Every native
session performs bounded measured search, strict arithmetic permits native-f32
cooperative matrices, and the compiled reference receives qualified
CUDA/HIP/XPU replay wherever available.

The performance result remains mixed: median strict inference and training
times are $1.83\times$ and $2.47\times$ PyTorch's across seven shared GPU
configurations. Search visits every eligible class in 606 of 624 paired-GPU sessions,
but the remaining gap includes limited kernel parallelism, excluded search
dimensions, and backend-specific implementation choices.
Replicated 1.7B results narrow the strict training gap without establishing
a uniform scaling advantage; accelerated large-model behavior is less favorable.

Meganeura's contribution is a compact, shared graphics deployment path in
which graph compilation can also perform measured kernel choice.
Measured choice improves several workloads, but startup and steady-state
costs still vary widely. RPL-U and MI300X also show why supported hardware
belongs alongside timing and numerical validity in a portability comparison.

\textbf{Analysis replay.}
The supplied \code{cohort.py} reads either the original archive directory
or the compact JSON bundle without executing archive contents. It checks
source identity, raw/joined agreement, retained-sample medians, numerical
gates, execution/search policies, and completed replication; it regenerates
the tables, figure, and per-condition CSV.
Run \code{python cohort.py records.jsonl.xz --check tables}.
This takes seconds with standard-library Python and requires neither GPU
nor network access. Compression changes no JSON values; the checker still
cannot reconstruct tensor elements not retained by the runners.
The pilot has its own frozen analyzer and does not enter the main aggregates.

\textbf{Rerunning.}
At the frozen Inferena revision, the platform setup script installs managed
Python and pinned vendor requirements.
\code{python scripts/p3hpc.py} collects the five-model cohort with native
tuning, default reference compilation, and applicable replay.
No \code{--no-max-autotune} flag is needed. Use \code{--backend cpu --qualify-only}
for a CPU correctness oracle on GPUs without a usable PyTorch path;
\code{--gpu} disambiguates multiple
installed GPUs. The optional
\code{--models SmolLM2-360M SmolLM2-1.7B} command collects the extension
on H100. Each campaign writes a manifest and a sibling \code{latest.tgz};
rename/copy that archive before collecting another device.
Failures stop collection and retain preceding records.
Rerunning reproduces the procedure, not the original timing noise.
Raw records retain environment, precision, memory-accounting bases,
20 call samples per phase, and validation diagnostics.
