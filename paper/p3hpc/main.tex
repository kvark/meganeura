\begin{abstract}
Graphics application programming interfaces (APIs) offer a common execution path for machine learning across
consumer and edge graphics processing units (GPUs), but their performance
and accelerator coverage need measurement. Meganeura is a compact native
compiler and runtime that lowers tensor graphs and automatic
differentiation to Vulkan and Metal kernels. We evaluate five workloads
on eight machines, including an NVIDIA H100 and Windows, with one PyTorch
source revision and independently qualified CUDA Graph replay.
Seven machines complete their selected conditions; two interrupted
campaigns retain partial Windows and larger-model results.
Across six complete GPU-reference configurations, median strict
32-bit floating-point training time is $2.41\times$ PyTorch's.
CUDA Graphs substantially reduce the apparent small-shape advantage,
while Meganeura's bounded compile-time search improves H100
SmolLM2-135M prefill by $1.38\times$.
Light-policy specialization takes 0.09--8.31\,s across arithmetic modes.
A 1.7-billion-parameter extension supplies preliminary scaling evidence;
the Intel integrated GPU and AMD MI300X expose opposite stack-availability
limits. Numerical gates, preparation costs, failure records, and
separate host/GPU diagnostics make the tradeoff explicit:
graphics APIs broaden deployment options, but do not eliminate
vendor-kernel advantages or guarantee access to every high-performance
computing (HPC) accelerator.
\end{abstract}

\section{Introduction}

Performance-portability layers such as Kokkos, RAJA, and SYCL let one
program target heterogeneous hardware
\cite{edwards2014kokkos,beckingsale2019raja,khronos2020sycl}.
Graphics APIs suggest a complementary substrate for machine learning
(ML): Vulkan exposes cross-vendor graphics and compute, while Metal
serves Apple platforms \cite{khronos2026vulkan,apple2026metal}.
An application already using these APIs can potentially share its driver,
resources, and execution queue with a tensor runtime.
That deployment advantage is useful from workstations to edge devices,
but does not establish competitive kernel performance or universal support.

We study \system{}, a compact native compiler and runtime that lowers a
typed tensor graph and its differentiated training graph to specialized
compute kernels. Blade supplies the Vulkan/Metal abstraction
\cite{malyshau2026barriers}. Model construction, graph transformations,
automatic differentiation, checkpoint semantics, and the runtime interface
remain common across devices; deployed applications require neither Python
nor a vendor ML runtime. Training and inference use the same compiler.
Optional empirical kernel selection runs inside session construction,
so deployment-time compilation can also perform bounded measurement.

The evaluation compares \system{} with PyTorch
\cite{paszke2019pytorch} at one source commit across CUDA, ROCm, XPU, MPS,
and CPU wheels. On NVIDIA, both default compilation and
\code{max-autotune} use explicitly captured and numerically qualified CUDA
Graphs; an uncaptured condition measures replay's effect.
This control matters: H100 SmolLM2-135M one-token latency falls from
4.24 to 1.28\,ms with replay alone, reversing the corresponding
Meganeura/PyTorch ordering.

Performance, portability, and productivity (P3) raise three distinct questions.
\emph{Performance} is elapsed
time against a declared valid reference, with arithmetic permissions and
preparation policy stated. \emph{Portability} includes whether that policy
can execute at all: PyTorch has no usable GPU path on the evaluated Intel
RPL-U system, whereas \system{} has no validated Vulkan path on the
attempted MI300X. \emph{Deployment efficiency} includes specialization
wait and runtime closure. We discuss debugging and maintenance burdens
qualitatively; these operational measurements are not a programmer-productivity
score \cite{lin2024productivity}.

Our contributions are:
\begin{itemize}
  \item A correctness-gated comparison of one native graphics-API ML
        compiler and runtime across eight machines, with a common PyTorch
        revision, controlled NVIDIA replay, and explicit incomplete and
        unavailable conditions.
  \item A measured preparation/performance tradeoff between light and
        searched compilation, including automatic kernel selection inside
        \system{}'s compilation and PyTorch's search-availability limits.
  \item Evidence separating replay effects, host command recording, and
        representative GPU kernel bottlenecks, together with a preliminary
        H100 model-size extension and concrete improvement experiments.
\end{itemize}

An arithmetic contract (Section~\ref{sec:contracts}) specifies permitted
numerical fast paths. Each device--workload--contract--policy comparison
is validated before its timings are admitted. GPU-versus-CPU support
comparisons and incomplete campaigns remain visible without being counted
as replicated GPU performance results.
This study includes datacenter hardware and up to 1.7-billion-parameter
models, but not production-scale large language model (LLM) training, optimizer updates,
distributed execution, or scientific simulation workloads.
The companion technical report develops the compiler and system design
in greater detail \cite{malyshau2026meganeura}.

\system{} executes a typed static tensor graph (Figure~\ref{fig:pipeline}).
Native builders and importers for Open Neural Network Exchange (ONNX)
and Neural Network Exchange Format (NNEF) construct the graph.
A deterministic greedy rewriter optimizes it; training adds reverse-mode
differentiation and, when requested by the application, a stochastic
gradient descent (SGD) or Adam update.
The benchmark measures forward, loss, and backward only.
An equality-saturation mode also exists, but is outside this comparison.

Code generation uses a small set of reusable kernel families:
pointwise expressions, reductions, general matrix multiplication (GEMM), convolutions and
their derivatives, and tiled attention. Shape, device capabilities,
and precision policy determine legal implementations and workgroup
geometry. The generated WebGPU Shading Language (WGSL) is validated
by Naga \cite{w3c2026wgsl}; Blade lowers it for native Vulkan/Metal.
Sharing Naga with wgpu does not mean using the wgpu runtime or executing
in a browser.

The compiler fixes a dispatch sequence and lifetime-based buffer reuse.
Each step records and submits that plan without graph rediscovery or
per-step tensor allocation; host command recording and synchronization
remain. It does not replay a native CUDA Graph.
This distinction is measured directly by the reference replay ablation.

With empirical selection enabled, session construction generates legal
alternatives, qualifies their numerical results on private scratch
buffers, measures successful candidates, and retains the incumbent when
none qualifies or improves performance. The measured implementation searches
a bounded subset of matrix and convolution tile choices. It follows greedy graph
rewriting; it does not jointly search graph representations and all kernel
families. Thus graph compilation and empirical kernel selection share one
deployment step, but broad autotuning coverage is an engineering
opportunity rather than an assumed property of this experiment.

\section{Methodology}
\label{sec:method}

\inferena{}, the open-source cross-framework harness, constructs matched
workloads, alternates engine order, synchronizes timing boundaries,
and records raw samples, outputs, gradient norms, revisions, and
environment metadata.\footnote{\url{https://github.com/kvark/inferena}}
It supplies kernels to neither engine.

\subsection{Revisions and reference conditions}

Every supplied campaign uses \inferena{} \code{17d13a3} and
\system{} \code{fcdd76d1}. All wheels report PyTorch 2.13.0 at source
commit \code{cf30153}, with Python 3.13.13. NVIDIA uses
\code{+cu130}, AMD \code{+rocm7.2}, Arc \code{+xpu}, Apple the MPS
wheel, and the RPL-U comparison \code{+cpu}.
Checkpoint revisions and hashes are recorded in the manifests.
Driver, host, and backend-library differences remain part of the platform;
a common PyTorch revision does not make those implementations identical.

Arithmetic and preparation are separate axes.
The \emph{light} policy pairs default PyTorch compilation with
\system{}'s empirical search disabled.
The \emph{searched} policy pairs PyTorch \code{max-autotune} with
\system{}'s bounded empirical selection enabled.
On CUDA, both use whole-phase graph replay. Default compilation without
replay is a separate ablation; Inductor's internal CUDA Graph mechanism is
disabled in every condition so the explicit switch controls replay.
The other compiler options retain their requested values
\cite{pytorch2026compile}. Light does not promise zero compiler or
vendor-library heuristics, nor a fixed startup deadline.

ROCm and XPU collect default compilation without graph replay after
requested max-autotune failed or did not finish during bring-up
(Section~\ref{sec:availability}). They are labeled light-policy availability
subsets. ROCm graph replay was not qualified in this protocol; this is
a limitation of the experiment, not a claim that HIP lacks graph support.
MPS and the explicitly selected CPU reference run eagerly.
Their results are not comparisons against compiled CUDA or XPU on the
same hardware.

\subsection{Workloads and timing}

The five principal workloads are SmolLM2-135M (decoder-only transformer),
the SmolVLA action expert (99.85M parameters)
\cite{shukor2025smolvla}, a scaled Stable Diffusion 1.x U-Net
(10.93M, not checkpoint-compatible with SD~1.5)
\cite{rombach2022ldm}, ResNet-50 at batch four
\cite{he2016resnet}, and the Whisper-tiny encoder (8.21M)
\cite{radford2022whisper}. Both runners use the same shapes,
deterministic inputs, scalar objective, and canonical parameter names.
The additional H100 campaign requests SmolLM2-360M and SmolLM2-1.7B.

Three phases are timed: full no-gradient forward, minimal-shape forward,
and forward--loss--backward (F+L+B), without an optimizer update.
SmolLM2 uses batch one, 128-token prefill and one stateless token.
There is no key/value cache; the latter is not an autoregressive serving
benchmark. Whisper's full and minimal shapes coincide.
Each phase has five untimed warmups and 20 synchronized host-wall samples.
Input loading and output/gradient readback occur outside the timing
interval. Buffers are initialized before execution; the retained planner
memory counts do not prove physical residency of every binding.

Each condition runs in three fresh process pairs, with alternating
engine order and rotated condition order. We report the median of the
three within-process medians, and retain their range and all samples.
Twenty calls in one process are not twenty independent replicates.
An interrupted campaign retains its completed pairs with their actual
replicate counts, but does not enter the complete-cohort aggregates.
Unreached runs are unmeasured, not framework failures.

\subsection{Arithmetic contracts}
\label{sec:contracts}

Strict f32 disables TensorFloat-32 (TF32) in PyTorch and cooperative-matrix paths in
\system{}, including native-f32 cooperative tiles. Tensor storage,
accumulation, and outputs remain f32.
The accelerated contract permits PyTorch's TF32 paths and
\system{}'s supported cooperative implementations, including
f16-input/f32-accumulate forward matrix, convolution, and attention work.
Derivative regions retain the full-precision policy.
The permissions are not identical numerical formats, and a device may
expose no implementation that engages them.
No quantization or persistent f16 tensor storage is enabled.

\subsection{Independent numerical gates}

Cross-engine forward validation checks shape, relative L2 error below
1\% over 256 evenly spaced output samples, and relative scalar-loss
error below 1\%. Backward validation additionally checks canonical
parameter sets, total-gradient-norm error, and relative L2 error of the
per-parameter norm vector.
Strict runs require both gradient errors below 5\%.
The frozen accelerated replication rule requires each error below 10\%
and the median of three process errors below 5\%, accommodating permitted
nondeterminism without accepting an unbounded outlier.
In fact, every completed pair in this cohort individually stays below
5\%; the largest parameter-norm-vector error is 3.31\%.
Norm checks can miss sign or elementwise errors, and sampled outputs
can miss localized errors.

CUDA replay has a separate, stronger gate against uncaptured PyTorch.
Preparation, warmup, capture, and execution share one dedicated stream.
Every participating output and gradient element is checked over consecutive
uncaptured calls and two consecutive replays.
Accelerated training uses eight uncaptured repeats; other phases use two.
The replay policy applies fixed whole-gradient RMS and maximum-error
bounds and records ordinary repeatability separately.
Capture or validation failures abort the requested condition; no eager
timing replaces a failed graph run.
The retained reports establish that this qualification ran, but do not
contain all tensor elements for independent offline revalidation.

\subsection{Light-policy performance}

Across the six complete GPU-reference configurations, strict median
ratios are 1.66 for inference, 1.26 for minimal shapes, and 2.41 for training.
The nominal win counts are 5/30, 10/30, and 4/30 respectively; one inference
win is the RTX~5070 ResNet near tie (0.998 before rounding).
With accelerated arithmetic the corresponding median ratios are
1.90, 1.31, and 2.49.
These populations include eager MPS and default-only ROCm/XPU;
they describe the declared available configurations, not an equal
backend or accelerator-efficiency comparison.

Radeon remains the strongest performance surface.
Strict RX~7900~XT inference is within $1.12\times$ PyTorch on four
workloads, with SmolVLA faster at $0.72\times$; its minimal SmolLM2
and SmolVLA shapes are $0.29\times$ and $0.35\times$.
The 780M wins three inference and two training comparisons in strict mode.
Convolution workloads remain its main deficits.
Arc~B570 also wins the two small transformer shapes, but its strict full
inference ratios span 1.22--3.13 and training spans 1.43--6.11.
Eager MPS wins all full-shape inference and training comparisons on M3;
Meganeura wins only the two small transformer shapes.

Qualified CUDA replay makes the NVIDIA comparison substantially harder.
On RTX~5070, strict inference ranges from parity on ResNet to
$2.74\times$ on Whisper, and training is $2.47$--$3.07\times$.
H100 has larger training gaps: $2.82$--$6.22\times$ strict and
$4.20$--$19.80\times$ accelerated. Accelerated ResNet is the largest:
PyTorch benefits strongly from its convolution fast paths while the native
derivative implementation remains expensive.
This is a measured engine/driver result; the table alone cannot assign
the gap to one instruction family or to barriers.

H100 accelerated ResNet inference is also unstable. Native process medians
in the light/replay condition are 11.93, 5.64, and 5.56\,ms, with some
individual samples near 19\,ms; training remains near 50\,ms.
The prescribed median is retained and this dispersion is disclosed.
The data establish a substantial deficit, but not a precise invariant ratio
or a diagnosis of the transient.

Table~\ref{tab:searched} gives the stronger searched CUDA comparisons.
Meganeura is slower in all 60 device--workload--arithmetic--phase

Native strict H100 135M prefill falls

Search acts during ordinary session construction.
It finds useful alternatives on measured models and is not equivalent

Extra preparation must be repaid by subsequent calls. Using the difference
of process-median preparation costs divided by the difference of
process-median call times, native 135M prefill amortizes search after

grows from 15.14 to 708.33\,s: about 1.14 million inference calls repay

validation. These estimates charge the recorded three-phase setup;
inference-only deployment may differ. They are workload-specific estimates, not deployment
deadlines or independent cold-start guarantees.

Requested max-autotune does not imply equal search coverage.
Pinned Inductor declines GEMM template search below its
68-streaming-multiprocessor (SM) gate,
including RTX~5070 (48 SMs) and RTX~3050 (20).
Other compiler choices still change: strict RTX~5070 ResNet inference
improves $1.23\times$ under max-autotune.
H100 (132 SMs) does execute the larger search.
Native tuning is narrower and bounded; the results are a cost/coverage
comparison of two automatic policies, not an equal search-space contest.

\subsection{Conditional performance portability}

\begin{table}[t]
\caption{Strict light-policy scores over six complete GPU-reference systems.}
\label{tab:pp}
\centering
\small
\setlength{\tabcolsep}{4pt}

For workload $a$, phase $q$, implementation $i$, and declared machine
set $S$, application efficiency is
$e_{i,a,q}(p)=t_{\mathrm{best\ valid},a,q}(p)/t_{i,a,q}(p)$.
We use the Pennycook metric \cite{pennycook2016metric,pennycook2021revisiting}:
\begin{equation}
P_{i,a,q}=\begin{cases}
|S|\big/\sum_{p\in S}1/e_{i,a,q}(p),&\text{valid on every }p,\\
0,&\text{otherwise.}
\end{cases}
\end{equation}
Best means the faster valid result of these two engines.
Table~\ref{tab:pp} uses the same six complete GPU-reference systems
for every workload and phase. Its final row is the arithmetic mean
of the five workload scores, not a new harmonic aggregate over applications.
Meganeura/PyTorch means are 0.55/0.96 for inference, 0.68/0.83 for minimal
shapes, and 0.39/0.98 for training.

This is explicitly conditional on a complete shared GPU comparison.
It excludes the CPU reference, interrupted Windows campaign, and MI300X
availability attempt; it cannot stand in for universal support.
If support is required across every attempted GPU, both stacks have
a known hole and hence a zero score: PyTorch on RPL-U, Meganeura on MI300X.
The availability results below are therefore as necessary as the
conditional performance scores.

\section{Edge Deployment Beyond the Matrix}
\label{sec:edge}

The matched matrix contains no Android reference, so Android contributes no
performance-portability score. A separately versioned physical deployment
tests whether the same source stack closes over an edge application rather
than only benchmark runners. DinoVision reconstructs the headset cameras'
live images from features computed by a vision encoder
(DINOv3~\cite{simeoni2025dinov3}). Figure~\ref{fig:dinovision} shows the
reconstructed view displayed on the headset. \system{} trains
a 2.01-million-parameter decoder on a host GPU, saves its parameters, and
loads them into a joined batch-one encoder/decoder graph on a Quest~3S. The
deployed 2.359-GMAC graph runs through the same graph representation,
compiler, memory planner, checkpoint format, and Blade runtime. Two
asynchronous eye sessions share Blade's Vulkan context and queue with the
OpenXR renderer.

\begin{figure}[t]
  \centering
  \includegraphics[width=0.73\columnwidth]{../figures/dinovision-quest3s.jpg}
  \caption{Quest~3S casting capture of DinoVision's live RGB
  reconstruction. This documents physical deployment; it is not a visual
  quality or capture-to-photon benchmark.}

We ask two separate questions: does the deployed graph reproduce the host
output, and how does its GPU work affect the renderer sharing the queue?
The first has an independent host/device gate. For one fixed public
RGB frame and identical weights, preprocessed patches are bit-exact; Quest
encoder output has relative $L_2=0.001059$ and the final reconstruction has
relative $L_2=0.000457$ against the host. An isolated synchronized run takes
96.78\,ms as one submission chunk. Splitting the ordered dispatch plan into
two chunks costs 4.1\% in isolation, but under a 90-second live stereo sweep
it raises application render submissions by 18.8\%, raises the lower-eye
update rate by 8.7\%, and reduces median worker latency by 20.2\%. Larger
chunk counts regress non-monotonically. The lesson is not that two chunks
are universally optimal; it is that graphics/compute co-tenancy exposes a
scheduling dimension that an inference-only benchmark misses, and the
shared graphics stack can expose that control without a second GPU runtime.

This case study establishes deployment closure and queue co-tenancy, not
on-device training or speedup over PyTorch on Android. Its weights, raw
samples, manifests, and full-resolution media are available in the public
\href{https://huggingface.co/mad-bot/dinovision}{DinoVision evidence
archive}; its \href{https://github.com/kvark/dinovision}{source code} is
public as well.

Kernel-level profiles also suggest actionable, general changes.
Qualified RTX~5070 ResNet traces concentrate work in scalar convolution
indexing and staging. A separate six-process-pair experiment specializes
immutable integer parameters and uses constant-divisor native arithmetic:
F+L+B falls 44.15$\rightarrow$34.44$\rightarrow$33.33\,ms,
with identical recorded outputs and unchanged independent f64 oracles.

the latter choice, amortized after roughly 256 training steps.
The prototype is retained at
\path{experiment/conv-native-division-2026-09-10}; it is not silently
installed in the final cohort.
A larger K-staging candidate passes the same numerical checks but
regresses performance, motivating measured choice rather than a global
constant change.

On token shapes, qualified Graphics samples concentrate in three
matrix--vector multiplication (GEMV) families, especially residual-add
and root-mean-square-normalization (RMSNorm) fused variants.
Changing the residual-add workgroup width and avoiding a packed-weight
copy improve separate resident-model experiments; the current production
tuner does not search those choices.
These results identify workgroup geometry and graph representation as
reusable search dimensions.
The previous M3 profile likewise located backward attention as a dominant
family and motivated an earlier Metal optimization
\cite{malyshau2026meganeura}.

None of these measurements establishes a removable Vulkan-barrier
percentage. Workgroup barriers inside shaders, resource dependencies
between dispatches, host submission, and waiting are different mechanisms.
In particular, wall time minus summed kernel time is not barrier cost:
execution overlaps, and instrumentation changes the schedule.
Our companion synchronization study demonstrates the sensitivity of
graphics abstractions to barrier policy \cite{malyshau2026barriers},
but predates the present resource tracking.
Per-kernel attribution on H100, AMD, and Intel remains incomplete;
the final cohort establishes their gaps, not a universal causal breakdown.

\section{Deployment Efficiency and Programmer Productivity}
\label{sec:productivity}

\subsection{Preparation as a deployment budget}

Native \code{compile\_s} covers graph construction, optimization,
autodiff, and native pipeline creation across the three sessions,
including measured search when enabled.
PyTorch \code{compile\_s} includes compilation and the first
specializations/executions of the requested phases.
Graph preparation and full-tensor qualification are recorded separately;
model loading, cross-engine validation, and the rest of process startup
are outside these fields.
Consequently these are declared preparation components, not a
time-to-first-answer measurement of an application.

Among complete light-policy groups, native specialization medians span
0.09--3.52\,s strict and 0.12--8.31\,s accelerated.
Compiled-reference medians span 7.01--78.32\,s strict; eager references
report zero compilation, not zero startup.
H100 searched compilation reaches 708.33\,s for strict ResNet.
Qualification is a separate research cost: for example, H100 135M
strict light graph validation takes about 11.72\,s across phases,
versus 0.29\,s graph preparation.
It would misrepresent both deployment and compiler performance to
charge these tensor comparisons as native shader compilation.

Cheap shader translation makes deployment-time search practical, but is
only one stage. A separate RTX~5070 compiler study measures median WGSL
parse calls of 141--172\,$\mu$s on three workloads; native driver
pipeline creation accounts for hundreds of milliseconds in their
session preparation.
A matched-domain f32 GEMM microstudy, after compiler warmup and with
fresh private disk caches, measures 30.8--31.2\,ms to prepare a native
candidate versus 100.4--166.6\,ms for Triton.
Both include machine-code preparation; allocation and execution are
outside these intervals.
This supports a few-fold candidate-preparation advantage in that
experiment, not a four-order-of-magnitude end-to-end claim.
Sources and reproduction commands are retained with the
compiler-stage experiments.\footnote{\url{https://github.com/kvark/meganeura/blob/main/docs/experiments.md}}

Compile-time autotuning is established practice
\cite{chen2018tvm,tillet2019triton}. The architectural opportunity here is
to combine graph compilation and bounded measurement inside a compact,
portable deployment runtime. The final cohort shows real gains from
that integration, while narrow candidate coverage and uneven returns
explain why empirical selection remains an explicit policy rather
than an unconditional startup cost.

\subsection{Availability is part of portability}
\label{sec:availability}

The RPL-U campaign explicitly uses eager CPU PyTorch; this is not a hidden
fallback from a failed GPU timing. Meganeura is faster in all five
strict full-inference comparisons (ratios 0.58--0.69), but its minimal
SmolLM2/SmolVLA shapes are slower than CPU (1.08/1.29).
The result establishes a working graphics-API GPU option in this
installation, not GPU-versus-GPU superiority or absence of Intel
integrated-GPU support in general.

Arc~B570 provides the separate, working XPU comparison.
Its pinned native dense embedding backward passes only 19,968 of
73,728 expected elements in the shape-derived exact probe.
The harness therefore selects and records PyTorch's equivalent dense
\code{index\_add} autograd formulation; all 73,728 probe elements pass.
The complete SmolLM2 pairs validate with this workaround.
Requested max-autotune did not finish its first ResNet qualification
within an hour, so the final campaign explicitly selects default compilation.

On the Radeon~780M, bring-up required an architecture override
(\code{HSA\_OVERRIDE\_GFX\_VERSION=11.0.2}) and disabling SDMA
(\code{HSA\_ENABLE\_SDMA=0}); both are recorded in the final manifest.
The preceding ROCm installation also encountered a missing pinned
Triton wheel. On both Radeon machines, requested max-autotune failed
while compiling diffusion training: convolution candidates exceeded
local-memory limits or timed out, and the remaining library fallback
was invoked without its required output buffer.
These are observed costs and limits of the vendor compilation path.
Default-mode measurements are useful deployable alternatives following
those failures, not a claim that exhaustive search was unnecessary or
would never improve performance.
The final archives record the omissions; the earlier bring-up failures
are documented separately from final timing records.

MI300X supplies the opposite availability boundary.
On the attempted cloud allocation, the report records a working
PyTorch/ROCm strict 135M run but no validated Meganeura result.
Mesa's documented RADV target is AMD hardware capable of graphics
\cite{mesa2026radv}. The older installed driver enumerated the accelerator
but rejected its graphics-queue submissions; a custom compute-queue/driver
experiment then reached real workloads but failed execution or produced
nonfinite gradients. Those patched-driver trials are diagnostics, not
a supported Vulkan comparison. The supplied evidence is a bring-up
report, not a complete paired timing archive.
It limits claims that graphics APIs reach every datacenter accelerator,
just as RPL-U limits claims about the vendor ML stack's reach.

\subsection{Application authors and backend maintainers}

Application authors express tensor graphs and reuse checkpoints across
backends. Backend maintainers still need expertise in WGSL, memory,
synchronization, and numerical behavior. Sharing the graphics stack
concentrates this specialist work; it does not eliminate it.
Eager PyTorch offers immediate tensor inspection, Python execution,
autograd hooks, and anomaly detection.
A static compiler can fuse away values or alias their storage, so
debugging may require preserved intermediates or a less optimized plan.
Meganeura provides named intermediate reads, graph-to-dispatch provenance,
first-nonfinite attribution, and same-kernel eager evaluation.
These help distinguish graph transformations, storage reuse, and kernel
errors. The same-kernel path is a diagnostic, not an independent numerical oracle.

Portable timestamp/provenance traces connect CPU work with GPU passes;
native tools remain necessary for instruction, occupancy, and stall analysis.
The CUDA failures and XPU probe illustrate why such observability matters
even when broad regression gates pass.
We did not measure developer-hours, learnability, maintenance effort, or
equivalent independent ports, and claim no quantitative productivity advantage.

An earlier, separately versioned Linux deployment audit found a
12.8\,MiB stripped native benchmark runner, versus 1.75\,GiB for the
PyTorch/Triton packages and 4.66\,GiB for the recursive CUDA runtime
dependency closure \cite{malyshau2026meganeura}.
The audit excludes weights, Python itself, ordinary OS libraries, and
the GPU driver. It is historical deployment evidence, not a new footprint
measurement of this cohort or a feature-equivalence comparison.
Section~\ref{sec:edge} supplies the complementary physical application check.

\section{Related Work}

Pennycook et al.\ define and later revisit the portability metric and
platform-set discipline used here
\cite{pennycook2016metric,pennycook2021revisiting}. Kokkos and RAJA encode
portable parallelism and memory policy in C++ libraries
\cite{edwards2014kokkos,beckingsale2019raja}; SYCL standardizes a
single-source heterogeneous C++ model~\cite{khronos2020sycl}. This study
instead fixes graphics APIs as the execution substrate and asks what a
domain compiler can recover. Lin et al.'s semantic-divergence metric also
motivates our restraint around the word productivity: our operational
measurements are not a substitute for their programmer-facing method
\cite{lin2024productivity}.

TVM, Glow, MLIR, and Triton established graph and kernel compilation for ML
\cite{chen2018tvm,rotem2018glow,lattner2021mlir,tillet2019triton}; RAF
extends whole-graph compilation to training~\cite{yu2023raf}. Burn~0.21 is a
broader Rust analogue, not a like-for-like compactness baseline: its documented
GPU targets span CUDA, ROCm, Metal, Vulkan, WebGPU, and LibTorch, with CubeCL,
Flex, and LibTorch CPU paths and decorators for autodiff, fusion, routing, and
remote execution~\cite{simard2026burn}. TensorFlow.js demonstrated
browser-resident training and inference~\cite{smilkov2019tensorflowjs}, and
systems for memory-constrained on-device training study a complementary
resource regime~\cite{lin2022ondevice}. Portable Rust autodiff is not the
novelty claimed here. The contribution is a frozen, validity-gated comparison
of one compact native graphics path across discrete, integrated, and
datacenter devices, coupled to profiles and deployment evidence.

TinyIREE treats artifact and runtime footprint as first-class deployment
results for embedded inference~\cite{liu2022tinyiree}; ExecuTorch deploys
exported PyTorch programs across mobile backends at scale
\cite{nachin2026executorch}. WebLLM and LlamaWeb demonstrate browser
graphics-API inference performance
\cite{ruan2024webllm,levine2026llamaweb}. \system{} is narrower in framework
breadth, but carries the backward pass, optimizer, and checkpoint through a
native Vulkan/Metal stack. The companion technical report gives the full
system and compiler account~\cite{malyshau2026meganeura}; the Blade study
isolates synchronization in the underlying graphics abstraction
\cite{malyshau2026barriers}.

\section{Threats to Validity}

The common PyTorch source revision removes the previous version mismatch,
but vendor libraries, drivers, host CPUs, operating systems, and permitted
fast paths differ. MPS is eager; ROCm and XPU are default-only availability
subsets with no qualified replay control.
The RPL-U CPU comparison, Windows partial campaign, and MI300X report
cannot be pooled into the six-system GPU performance aggregate.
Conditional scores would overstate universal portability if the
availability holes were omitted from the interpretation.
H100 records Vulkan driver 570.195.03 with CUDA~13 wheels.
NVIDIA's forward-compatibility libraries can support this combination
\cite{nvidia2026compat}, but their loaded identity is not retained.
This provenance gap is not a diagnosis of the capture failure.

The larger H100 models retain only one strict process per successful
condition. They improve parameter-count coverage but do not establish
production LLM scaling: batch and sequence length remain small, decoding
has no cache, and training excludes optimizer state and distributed
communication. The diffusion graph is reduced, Whisper omits its
decoder, and ResNet uses inference-folded normalization.
The failed searched 1.7B condition provides no paired time;
later unattempted conditions supply no success or failure evidence.

Fresh processes have empty private TorchInductor/Triton caches, while
persistent driver and vendor-library state remains as found.
Rotating condition order mitigates rather than removes history dependence.
Preparation and break-even estimates therefore describe naturally warm
installed systems, not independent first-use cold starts.
Light need not erase a driver/library choice established earlier.
H100 native accelerated preparation itself varies substantially between
processes, reinforcing the need to retain the process-level records.

Three process replicates improve on a single-process measurement but
do not characterize a platform population. CPU power policy, cloud
co-tenancy, thermals, and timing-window length can affect results.
The H100 accelerated ResNet inference transient is retained without an
unsupported root-cause assignment; CPU-reference latency also varies.
Separate longer-warmup experiments expose host clock sensitivity, so
the fixed 5/20 protocol measures warmed short-window latency rather than
guaranteeing sustained throughput. No outlier was removed from these
campaigns to improve a ratio.

Strict f32 constrains permissions, not operation order or bitwise identity.
Cross-engine sampled outputs and gradient norms can miss localized or
sign errors. Full-element CUDA replay qualification checks PyTorch
against itself and does not strengthen the cross-engine gate into a
full-gradient comparison.
All 366 completed pairs individually pass the 5\% gradient bound;
incomplete groups are still not promoted to completed replication.

Planner allocation sizes, allocator reservations, and process/driver
accounting have different meanings. A host-visible Vulkan allocation can
also occupy device memory; the planner's device-local category alone
does not prove physical heap placement.
Earlier explicit-placement diagnostics show that a nominally fitting model
can still encounter host-memory fallback on another configuration.
The final H100 extension is not a controlled placement or PCIe study.

Development profiles and optimization ablations carry separate source
revisions and sometimes explicit resident-parameter controls. They explain
representative mechanisms and proposed remedies, not every final-cohort
gap. Work on several vendors informed this compiler; the experiment does
not isolate general architecture from accumulated manual engineering.
Nor do footprint and preparation metrics measure programmer productivity.

\section{Conclusion}

A single Vulkan/Metal compiler and runtime executes matched ML inference
and backward workloads across heterogeneous consumer systems and H100,
with a working Windows path demonstrated before a reference capture
failure. A common PyTorch revision and verified CUDA Graph replay make
the performance comparison substantially stronger.
They also narrow its outcome: median strict training time is
$2.41\times$ PyTorch's on the six complete GPU-reference systems,
and the searched CUDA reference wins every measured phase comparison.

Meganeura's opportunity is compact deployment, broad graphics-driver
access, and cheap enough specialization to include measured kernel choice.
The H100 135M prefill gain of $1.38\times$ demonstrates that compile-time
search can help without model-specific code.
The partial 1.7B results show a narrowing training gap but no uniform
scaling advantage; profiles identify host recording, convolution
specialization, and matrix/vector kernels as distinct improvement targets.
Finally, RPL-U and MI300X show why neither graphics APIs nor vendor ML
stacks can claim universal availability.
Performance, numerical validity, preparation cost, and actual support
must be reported together.
